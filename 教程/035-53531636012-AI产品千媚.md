## 1. 核心认知（先看这一节）

- **关键细节：让它出补货方案时会触发人工审批，在聊天里说 “同意” 不会执行，必须从指定审批入口确认 —— 因为补错库存、改错价格会直接造成损失**（2026-09）
- **关键背景：Palantir 的 Ontology 诞生在大模型之前，机器理解力弱，所以业务概念、关系、规则必须提前显式定义**（2026-09）
- **作者的核心观点：这件不到 50 美元的小事，让她第一次具体感受到 “主动型 Personal Agent” 的价值**（2026-10）
- **作者的核心判断：从大模型到智能体，本质是 “从只会说到能做事” 的跨越，是从玩具到工具再到生产力的质变**（2026-02）
- **知识的沉淀过程，本质上是从骨架长出分支，再长出枝叶，最终进化为网状知识图谱的过程**（2026-04）
- **结尾作者埋了第 3 天的伏笔：聊了两天，上下文窗口满了、记忆被压缩，Claude 开始 “降智”，所以光有方法不够，还得学会管理上下文**（2026-05）
- **核心问题：长任务三种翻车方式 作者归纳了 Claude 做长任务时的三类失败：一是 “白烂”，让读 50 篇报告，读到 30 多篇就说 “干完了”**（2026-06）
- **核心结论：agent loop 本身没变，仍是 “理解任务→选工具→执行→接收结果→再判断”**（2026-08）
- **作者借此提出核心判断 ——模型变强后，过去用来补短板的提示词反而成了负担，并总结了 6 条新原则**（2026-08）
- **最难的是 99%，因为企业 AI 一次出错就可能造成严重后果，系统接得越多，权限审计、回滚、人工接管越复杂**（2026-09）
- **长期记忆跨会话记住偏好、性格，本质是 "AI 时代的用户画像"，让 Agent 从工具变成数字伙伴**（2026-02）
- **作者的核心结论是：OpenClaw 并没有发明新技术，它的爆火来自把已有能力组装成一套本地化、高度解耦的 Agent 平台**（2026-03）
- **多 Agent 架构的核心结论是：不是越复杂越好**（2026-03）

## 2. 实操方法（照着做）

1. 作者最推崇 ReAct（Reason 分析拆解 → Act 调工具执行 → Observe 看结果再调整），以 "用户要退款" 为例：第一轮查订单状态确认可退，第二轮创建退货单并调接口，最后同步结论（2026-02）
2. 第三层：Context 解决 “断片” 客户刚问完 iPhone，接着问 “最便宜多少钱”，客服却不知道在说哪款 —— 因为大模型本身没有记忆，每次对话都是独立的（2026-02）
3. 她的核心观点是：这套标准表面在讲招人，实际是用 “大模型怎么变聪明” 的逻辑，重新讲人该怎么成长 ——AI 时代最危险的未必是不爱学习的人，而是特别擅长考试、熟悉流程、依赖过去成功经验的人（2026-07）
4. 作者自评体验不错，卡点是最后生成环节很慢，因为要汇总的内容太多，暂未想到优化方案，也在向观众征集思路（2026-03）
5. 以推荐系统为例，其核心目标是解决推荐精准度的问题，因此适合采用从前到后的学习顺序：先学习召回，再学习排序，最后学习重排（2026-04）
6. 用第三方商城和后台的，要看平台开放了哪些接口，没操作接口就先接查询和建议（2026-09）
7. 开发一个 Agent 的第一步不是直接写代码，而是选择合适的开源技术框架（2026-11）
8. 它最初是为了让人类与计算机沟通而设计，现在则成为AI与操作系统交互的关键（2026-04）
9. 1971年，贝尔实验室工程师造出Unix操作系统，出现第一个hell Thompson shell，只能执行基础命令（2026-04）
10. 这是「7 天掌握 Claude Code」系列的第 2 天，主题是给 AI “员工” 立规矩：从 “一句话派活” 转向 “先探索、再规划、后编码、最后提交” 的完整开发流程（2026-05）
11. 例如，让 AI 提炼群聊讨论并创建复盘日程，背后至少包含了读取消息、提炼待办、创建日程、发送结果等五个步骤（2026-07）
12. 召回时先取最近更新的最多 200 份记忆的标题和简介，交给另一个 Sonnet 模型筛出最多 5 份最相关的，再给主 agent（2026-08）
13. 也有人算账 —— 一次循环做到 95%，加上多轮验证补最后 5%，时间可能增加十倍以上（2026-08）
14. 作者把 Anthropic 今年 1 月的 Agent 评测文章和阿里技术团队的评测体系工程实践放在一起讲，最后给出一张评测指标地图（2026-09）

## 3. 常见误区与坑

- ✗ Auto Compact：最后才整段重写，单独发起一次不能调工具的摘要请求，保留用户请求、关键判断、读写过的文件、错误修复、进度和待办（2026-08）
- ✗ 作者最后给的修复原则是先修已确认的问题，再做增强：基础数据坏了却去调 TOPK、换模型，只是在补偿上游错误（2026-10）
- ✗ 一个值得留意的边界：RAG 能显著降低幻觉，但并不能完全消除 —— 检索到错误或过时资料时，模型仍会照着错的内容回答，所以知识库的维护和答案溯源同样关键（2026-02）
- ✗ 这套方法里最容易踩坑的其实是 CHALLENGE 那一步 ——AI 很擅长把推断写得像事实，你想先看它怎么给结论打证据标签，还是先看 MAP 阶段怎么界定 “最小 Agent Loop”（2026-08）
- ✗ 三条设计原则：轻量化（别把人类经验硬编码，只定义工具边界和护栏）、权限渐进式披露（Vercel 删掉 80% 工具后，步骤更少、token 更省、成功率更高）、把 Harness 视为数据集（失败和漂移都是训练素材）（2026-03）
- ✗ 代价是总计算量上升，token 成本约为单 Agent 的 3—10 倍，所以作者提醒 “杀鸡不要用牛刀”（2026-03）
- ✗ Agent 要理解需求、排步骤、调工具、读结果、改文件，错误可能出现在执行链路任何一环 —— 订单找错、金额传错，后面工具调用再顺利也是错的（2026-09）
- ✗ 博主登录确认仍用不了，dots 建议先取消订阅避免续扣、再联系客服退款，并持续跟进客服邮件、在关键节点回来二次确认（2026-10）
- ✗ 作者特别点出一个常见误区：很多企业按原组织架构拆 Agent（产品一个、前端一个、后端一个）再用编排系统串起来，本质只是把 “人对人交接” 换成 “Agent 对 Agent 交接”，上下文照样丢（2026-10）
- ✗ 在这样的环境下，最重要的是保持自己的学习节奏，明确不同阶段的学习内容，不要被外界热点带着走，避免陷入 “什么火学什么” 的焦虑循环中（2026-04）

## 4. 关键零散结论

- 作者认为，第一次让 Claude Code 开发用户管理系统时，5 分钟就写完了，但风格和功能都不对，问题不在模型能力，而在工作方法
- 评测必须覆盖一次完整任务：说了什么、做了什么、系统最终变成什么状态
- 三种评分方式的适用场景，以及 LLM as a judge 的四个原则和人工校准的作用
- 第三方 Skill 尽量选官方或高 star 的，装之前看一眼脚本内容
- 第三方 Skill 最省事的办法是把 GitHub 链接直接丢给 Claude Code 让它装
- 自有商城和后台的企业自主性最高，重点在接口打通 ——“接口本身都不确定，换再强的模型也没用”
- 第二梯队是 Newsroom（公司动向、模型发布、政策立场）和 Toolbook（工具调用、评测、代码示例，开发者可提到第一梯队）
- 他判断 AI 现在处于第一阶段尾巴、第二阶段开头，标志是 Token 成为公认的计量单位（有了 “度量衡” 才能规模化），以及 Agent 能自己干活
- 第一代 Naive RAG（三段式）：建索引（文档切块→向量化入库）→ 检索（问题向量化，取 Top-5 片段）→ 生成（片段 + 问题交给大模型）
- 常规电商客服用第二代 Advanced RAG 就能解决 80%–90% 的问题
- 作者最初想直接分享在线文档链接，但后来发现这种形式存在一定的局限性
- 前四层开源方案密集可直接用，可观察性与治理覆盖最薄，博主据此给出选型与研究方向建议
- 要区分哪些规则必须常驻、哪些结果只需摘要、哪些历史可压缩、哪些结论要写进计划
- 原则是每类信息只在最合适的位置出现一次
- 必须更早进入真实环境，用真实数据和场景验证、暴露问题、快速迭代
- 可以问 “最近两周销售数据有什么变化、主要由哪些品类带来”，让它分析定位问题、给降价促销建议，或做日常巡查汇总库存与订单异常
- 作者认为最值得看的设计是：连续任务由一个主 Agent 承接，Skill 按需提供业务方法
- 内容分四类 ——agents（智能体构建与应用）、Claude Code（开发方法与最佳实践）、企业应用案例、产品公告
