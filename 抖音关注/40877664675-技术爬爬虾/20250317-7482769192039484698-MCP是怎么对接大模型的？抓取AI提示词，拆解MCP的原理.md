这条视频是博主「技术爬爬虾」通过 Cloudflare AI Gateway 抓包实验，拆解MCP 协议对接大模型的底层原理，还在开头主动更正了此前的表述：MCP 和 AI 的对接方式没有统一标准，会根据客户端不同而变化，比如 Cline 依赖系统提示词实现，5ire 则是基于 function call 功能完成。

博主先把 MCP 定义为 “AI 大模型的标准化工具箱”，并抛出核心疑问：大模型如何感知工具箱里的工具、调用参数是什么，MCP 和 function call 的关系是什么，是不是只有支持 function call 的模型才能用 MCP。随后他用 Cloudflare 的 AI Gateway 搭建代理，让所有大模型 API 请求先流经 Cloudflare 留下完整日志，再搭配 VSCode 里的 Cline 插件、OpenRouter 的 API 和免费的 DeepSeek V3 模型，安装了一个 Python 编写的时间类 MCP Server，完成基础环境配置。

通过抓包查看请求日志，他发现 Cline 是直接把 MCP 的工具列表、调用规则完整写入系统提示词传给大模型，大模型返回工具调用指令后，Cline 再去调用本地的 MCP Server 拿到结果，最后把结果整理后二次传给大模型输出最终答案。这套机制也解释了 MCP 通用性极强的原因：它不需要大模型具备额外的特殊能力，只要能读懂提示词就能使用。

后续博主又用不支持 function call 的 DeepSeek R1 模型做验证，结果依然能成功调用 MCP 工具获取时间，直接证明了 MCP 和 function call 是相互独立的两套机制，没有依赖关系。MCP 的核心价值是把各家大模型不统一的 function call 标准，整合成了一套通用的协议，让几乎所有大模型都能接入这套标准化工具体系。

评论区也围绕技术细节展开了不少讨论：有观点指出多 MCP 服务会占用大量上下文、消耗更多 Token；也有开发者分享仅靠提示词调用工具容易出现格式错误、成功率低的问题，认为原生 function call 会更稳定。
