传统 RAG 的核心运行逻辑

视频先讲清了检索增强生成的完整流程：用户上传资料后，程序会先把文本拆分成多个文本块，用嵌入模型将每个文本块转换成固定维度的向量，存入向量数据库；用户提问时，问题本身也会被向量化，通过纯数学相似度匹配从库中召回匹配度最高的几个原文片段，最后把这些片段和问题一起传给大模型做归纳总结。作者特别点明：RAG 的回答效果很大程度上不取决于大模型本身，而是由文本块的检索精度决定。

传统 RAG 的三大典型痛点

作者通过 Cherry Studio 的实际搭建测试，逐一验证了三个核心缺陷：

切片方法粗暴：默认使用递归文本分割器按固定字数分块，经常把完整句子拦腰斩断，AI 拿到被拆碎的段落很难理解上下文关联，直接影响回答准确性。
检索精度不足：向量匹配是纯数字的相似性计算，无法完全对应文字的实际语义，测试 “张飞兵器” 时，前几条召回结果都和丈八蛇矛无关，真正相关的内容被排到了第四位。
缺乏大局观：面对结构化数据的统计类查询，比如统计 300 条学生数据的总人数、筛选特定条件的记录，RAG 只能召回零散的文本碎片，根本无法完成全局统计，测试时甚至把 300 个学生误判成 74 个。
三个不用编程的进阶优化方案

视频给出了可直接落地的改进手段，全程无需写代码：

接入重排序模型：先通过向量库做粗召回，再用专用重排序模型对结果做二次语义分析、重新排序，测试后 “张飞兵器” 的相关内容直接排到首位，匹配分数从 51% 提升到 70%。
用 MCP Server 对接关系型数据库：把结构化数据存入 PostgreSQL，在 Cherry Studio 中配置 MCP 服务器，让 AI 直接通过 SQL 语句完成精准的统计、多表联合查询，彻底解决传统 RAG 处理结构化数据的短板。
借助超大上下文模型：直接把完整资料拖进 Gemini 这类百万级 Token 窗口的模型对话框，比如把全本修改过的《三国演义》直接上传，AI 可以精准定位到自定义修改的 “张飞造丈九棒棒糖” 的原文位置，单本全本《三国演义》仅消耗 54 万 Token。
