这是一期讲 Agent 上下文占用率的科普视频，作者是「一启 - AI」。核心观点是：很多人用 Codex、Trae、WorkBuddy 这类 Agent 时只看结果，忽略了任务执行后显示的 “上下文占用率”，而这个参数直接决定 Agent 好不好用、能不能用。

为什么值得关注

作者先讲了个前提：大模型本身没有记忆，是无状态的。你觉得它能记住前几轮对话，是因为每次提问时，系统会把历史对话一起打包塞进输入里，也就是 “伪记忆”。但输入长度有上限，这个上限叫上下文窗口，超出部分会被直接丢弃，所以聊到二三十轮后，早期内容就 “失忆” 了。

即便现在主流模型宣称支持 100 万上下文，作者认为依然不够用，他举了两个实测：

在 WorkBuddy 里只发一句 “你好”，上下文占用率就接近 20%（实际消耗 3.8%）；
让它读一份 Excel 并产出 HTML 分析报告，20 万窗口里花掉 10 万，等于一个任务吃掉 50%。

占用率高的原因

Agent 不是一次性想好全部步骤，而是拆成很多步，执行完第 1 步才决定第 2 步。每一步内部都要调用大模型做决策，而每次调用都要重新组装一份完整上下文：系统提示词、工具定义、固定记忆或 skill、对话历史、当前任务。前几项基本不变，真正不断膨胀的是对话历史—— 每一步的工具调用和产出结果都会累积进去，到第 15 步时已经非常庞大。

评论区补充的实用经验

有用户说 Claude Code 跑到 97% 占用仍能继续执行任务，停在 99% 直到完成；也有人反馈 DeepSeek 虽支持 1M，但到 200K 左右效率就开始下降。关于 WorkBuddy，评论提到对话历史存在项目里的 remand 文件中，上下文过长导致幻觉时可以新开会话把它当项目记忆传入；它也会自动压缩上下文、清空早期记忆。这些属于个人使用反馈，不是官方结论。
