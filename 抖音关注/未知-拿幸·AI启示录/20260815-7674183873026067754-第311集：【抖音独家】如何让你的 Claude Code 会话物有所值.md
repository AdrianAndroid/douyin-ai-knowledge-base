这条视频讲的是 Claude Code 的省钱逻辑：同样修一个 Bug，有人花 3 块、有人花 30 块，差距不在模型变笨，而在提示缓存有没有被保住。作者称依据是 Anthropic 官方博客一篇《如何让你的 Claude Code 会话物有所值》的文章，并把它翻译成大白话：大部分 Token 是白烧的。

钱是怎么被吃掉的

每次请求分两段：预填充把系统提示词、CLAUDE.md、全部对话历史一次性读进去（输入 Token，可并行处理）；解码则一个字一个字往外吐（输出 Token，串行跑模型），所以输出比输入贵约五倍。麻烦在于每轮请求都要把前面所有对话重新塞一遍，到第 40 轮就等于重读前 39 轮，增长接近平方级。

缓存是那个杠杆

只要这次请求开头和上次一字不差，服务器直接复用上次算好的结果，只收正常价的十分之一；代价是首次写入缓存最多多花两倍，但只花一次。死穴是必须从最开头完全对上，中间一变后面全废。作者点名会让缓存报废的操作：中途切模型、切推理强度、开 fast 模式、跑 compact，以及闲置超时（订阅用户缓存能活几小时，API 默认只有五分钟）。最容易踩的是 Plan 模式—— 每进出一次等于切一次模型，缓存跟着报废。

第二笔账：上下文膨胀

Claude 读的每个文件、跑的每条命令输出都会进历史，之后每轮都带着重发。官方有个兜底：输出超过 3 万字符自动写进临时文件、对话里只留摘要，但 3 万以下没人管 —— 比如测试框架打印 400 行通过记录，就会赖在对话里陪到最后。

作者总结的省钱做法

修完一个 Bug 就 /clear，别把上个任务的探索痕迹带进下一个
引用文件用 @ 挂进消息，别让它满仓库乱翻
给啰嗦命令加安静参数（如测试只打摘要）写进 CLAUDE.md
大文件、大日志交给子 Agent，独立上下文跑完只带回结论
休息前趁缓存还热就 compact；新会话先 compact 一次，看看 CLAUDE.md 和 MCP 工具定义占了多少
最后几轮跑偏了别急 compact，用 rewind 砍掉，前面缓存原封不动
