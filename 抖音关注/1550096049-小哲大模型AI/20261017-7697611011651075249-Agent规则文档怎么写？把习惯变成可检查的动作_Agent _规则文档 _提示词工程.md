这条视频是博主小哲讲「Agent 规则文档」怎么写，核心观点一句话：规则文档不是越长越好，而是把反复需要的工作习惯写成可执行、可检查的动作。

它解决什么问题 作者先区分了两件事：模型能力是一回事，执行过程中怎么做选择是另一回事。Agent 接一个任务往往要连续做很多决定 —— 先查什么资料、哪些内容保留、哪个工具做完还要不要改 —— 前面交代的规则会影响后面一连串选择。短任务临时说一遍可以，但任务拉长后对话信息变多，要求容易被遗漏，用户也容易忘记重新交代。规则文档的价值就是给这些要求一个稳定的维护和加载入口。

作者也提醒了边界：长期保存不等于绝对优先，更不等于模型一定照做。不同工具对规则的加载时机、作用范围、优先级设计不同，所以要先确认工具支持哪些规则文件、在哪个目录生效、有无长度限制、冲突怎么处理；权限不能靠一句 "这条最重要" 无限提高。文件位置最直接的办法是查工具说明，或让 Agent 帮忙定位，常见做法是用 Markdown 文件。

怎么写才具体 作者给的方法是把抽象期待改成可观察的动作，画面里也做了对照：

抽象期待	具体动作约定
"设计要高级，要有审美"	"开始设计前，先参考知识库里已有的配色和构图"
"你要认真负责"	"交付前检查文件是否完整，打不开的文件先修好"

判断标准是两问：这句话能不能指导一个具体决定？能不能观察到执行结果？只能表达态度、不能改变动作的，就继续写具体。

两个容易踩的坑

别一次列一百条：凭空想的要求未必对应真实问题，规则太多增加阅读和维护负担，冲突时 Agent 反而不知道该按哪条执行。作者的做法是让规则从实际协作里长出来 —— 第一次没按预期先纠正，第二、三次还遇到同类问题再写成规则。
别只加不减：习惯变了要回头删过时内容、合并重复要求。另外全局规则、项目规则、子目录规则的作用范围要分清，通用习惯放全局，项目约定放项目，局部要求放对应目录，具体遵循工具的作用域机制。
