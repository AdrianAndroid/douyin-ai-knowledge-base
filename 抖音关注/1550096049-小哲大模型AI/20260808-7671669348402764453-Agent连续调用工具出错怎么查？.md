这条视频是博主小哲讲的一道 AI 开发面试题：Agent 连续调用十个工具后出错，怎么快速定位错在哪一步。他的核心观点是，这题考的不是 “会不会打日志”，而是有没有做 Agent 工作流的 Trace（可观测性）设计—— 因为 Agent 的失败往往不是单点异常，而是判断、调用和状态连续偏移的结果。

四层排障思路

步骤标识：每次模型推理和工具调用都挂在同一个任务级 trace 下，并有稳定的 step_id。没有 step_id，排障时只能看到一堆散日志，分不清哪一步影响了下一步。
输入输出快照：调用前记录模型准备传的参数及其来源（用户、记忆、上一步工具结果），调用后记录原始返回和模型加工后的理解。作者举的典型坑是：工具返回 “受理中”，模型却理解成 “已完成”，这种语义偏差只有存快照才能定位。
错误分类：工具失败、业务失败、权限失败、格式失败、超时、用户取消、证据不足不能都记成 failed，因为对应的处理不同 —— 有的可重试，有的要补偿，有的转人工，有的直接终止。
回放与评测：线上 bad case 要能重放当时的上下文、工具结果和模型选择，再用修复后的策略跑一遍，否则无法证明修复有效。链路越长，越要看路径是否合规、成本是否异常、重试是否放大副作用。

一个具体例子：订单处理十步链里，查库存成功、锁库存成功、发券失败，系统要能看出是券模板失效，而不是整个订单主流程失败。

面试回答模板：用任务级 trace 把模型推理、工具调用、权限校验、返回解析和最终状态串起来，出错后按 step_id 定位是参数、工具、业务语义还是后续判断出了问题。作者还补了两点加分项：trace 要和告警绑定，能按版本和用户群拆分语义失败率、重试次数等指标；trace 本身要做采样和脱敏，高风险任务全量记录、低风险按比例记录，敏感字段只留哈希或摘要。
