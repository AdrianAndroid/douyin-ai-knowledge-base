这是博主「小哲大模型 AI」讲的一道 AI 面试题：什么时候该用多 Agent 系统。作者的核心观点是：不能靠 “任务越复杂越适合” 来回答，真正要看的是并发收益和上下文需求这两项指标。

为什么 “堆架构” 是错的

作者先还原了典型的多 Agent 设计：主控 Agent 拆任务，再派给写代码、做测试的 Agent。放到生产环境里，每调用一次大模型，延迟通常是秒级；节点之间还要来回传消息，整套流程跑完，用户可能得等半分钟。Token 成本成倍上涨，出 bug 时也很难定位是哪个环节开始出错。作者认为，面试官最反感的就是这种为了显得先进而强行堆架构的过度设计。

两个场景划出边界

智能客服查退款进度：识别意图 → 查订单状态 → 组织回复，三步严格串行，不知道订单号就查不了库。若拆成 “查询专员 + 回复专员”，中间凭空多一次模型通信，延迟可能从 3 秒变成十几秒。这类线性任务，单 Agent 加工具调用最干净高效。
企业级代码安全审计：几万行代码全塞进单 Agent，上下文窗口会被撑爆，模型看完后面就忘了前面。这时拉起安全检测、性能、规范三个 Agent 并发扫描，互不等待，最后交主控 Agent 合并。多 Agent 的价值就在于把庞大上下文切碎，靠专业分工和并行突破单模型上限。

一句话结论：单 Agent 打低延迟、低成本的 “闪电战”，适合线性任务；多 Agent 打突破上下文和专业分工的 “阵地战”，适合可并行拆解的任务。真实工作里先用单 Agent 跑通原型，别一上来就过度设计。

需要补一句边界：视频里的 “3 秒变十几秒”“半分钟” 是作者为说明问题举的示意数字，不是实测数据；多 Agent 也不是只有成本劣势，它在上下文隔离和故障隔离上确实有收益，只是要先确认任务真能并行。

主控拆任务、节点互传消息，延迟和 Token 成本一起涨，出 bug 还难定位。

不看任务 “听起来多复杂”，只看能否并行、是否撞上单模型上下文上限。

三步强串行依赖，拆多 Agent 只会多一次通信、多几秒等待。

三个 Agent 同时扫注入、内存泄露、代码风格，再由主控合并结果。
