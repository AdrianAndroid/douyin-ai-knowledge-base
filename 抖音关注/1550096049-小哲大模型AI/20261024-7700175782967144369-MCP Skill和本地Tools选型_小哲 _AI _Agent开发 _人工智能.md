这是博主小哲讲 Agent 开发面试题的一条口播科普视频，核心观点是：MCP、Skill、本地 Tools 三者不是 “外部 vs 本地” 的替代关系，而是三个不同层面的东西，面试官问这题是想看你有没有真写过 Agent 的工具调用。

先纠正一个常见误区 很多人答 “MCP 对接外部工具，Skill 和本地工具只能在本地用”，作者认为这属于死记概念，一追问业务场景就露馅。三者的真实定位是：

本地 Tools：直接写在 Agent 服务内部的函数逻辑，和 Agent 跑在同一环境，比如取时间、做基础计算，调用即完成，解决 “进程内能直接跑什么”。
Skill：对工具能力的封装与描述，只写功能、入参、触发前提，本身不执行任何操作，交给大模型判断要不要调用；底层挂本地代码还是外部接口都行，同一份 Skill 定义可以换实现。
MCP：一套通信协议，不含业务逻辑，只负责 Agent 与外部独立程序之间的指令下发和结果回传，核心是保障跨进程安全互通。

运行特性与取舍 本地 Tools 链路短、无网络开销、响应最快，但和 Agent 强耦合，加工具要改代码重启，第三方程序用不了，适合功能简单、改动极少的小工具。MCP 则相反：外部程序独立运行，新增工具只需启动对应 MCP 服务，第三方程序只要实现 MCP 标准就能接入，代价是多一层进程间通信和序列化开销。

作者举的例子是图片处理：把图片逻辑塞进 Agent 会造成代码臃肿、图片库版本冲突甚至整个 Agent 崩溃；改成单独起一个图片 MCP 服务，Agent 里只写一段 Skill 描述，模型读 Skill 再通过 MCP 调外部程序，Agent 本身零图片依赖。

实战建议 优先用简洁自包含的方式，链路短、速度快；但不管底层是本地还是 MCP，对外给模型的能力都统一封装成 Skill，模型只理解 Skill。只在四种情况才上 MCP：工具依赖过重易版本冲突、第三方现成程序不想重写、希望工具独立部署、需要隔离权限防止外部工具崩溃拖累 Agent。反过来，大量高频小工具全走 MCP 会增加通信开销和失败率，不建议硬上。

一句话总结作者的说法：本地 Tools 管快速执行，Skill 是大模型识别工具的核心，MCP 是 Agent 与外部程序沟通的桥梁。

作者开始正面拆解，指出新手常踩的坑是把外部能力硬转成本地 Skill，或让所有工具都走 MCP，结果扩展繁琐或调用链路拉长、参数解析报错。

逐个定义本地 Tools（进程内函数）、Skill（面向模型的描述层）、MCP（跨进程通信协议），强调三者无优劣替代关系。

对比本地 Tools 的短链路强耦合、Skill 的可切换底层实现、MCP 的独立部署与通信开销，并用图片处理举例说明。

给出 “默认自包含、统一封装 Skill、必要时才上 MCP” 的选型原则，并提醒高频小工具不要强行走 MCP。
