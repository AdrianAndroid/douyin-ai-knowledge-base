这是「小哲大模型 AI」的面试题拆解系列，主题是字节二面题：RAG 如何处理 PDF 文件。作者的核心观点是：把 PDF 当纯文本抽出来、切块、灌进向量库，只是 “跑过 demo” 的水平；生产级方案要把 PDF 当成一条多模态文档理解流水线，分四层来做。

第一层：先识别 PDF 类型，别急着抽文本

原生文本 PDF：文字由文本指令直接绘制，可用解析器精准提取并保留坐标位置。
扫描件 PDF：本质是一张张图片，容器里没有字体，必须走 OCR（如 Tesseract 或更强的文档识别模型）。
图文混排 PDF：论文里的票据、架构图、复杂表格，光抓文字不够，要调用多模态视觉模型 “看图写描述”。作者举了 Anthropic Claude 的 PDF 支持为例 —— 它不解析结构，而是像人眼一样整页阅读，把表格线、图像和文字作为一个整体理解，比 “抽文本 + 单独 OCR” 拼接更不易割裂。

第二层：还原文档骨架 用文字坐标和字号推断标题层级，用线条和空白还原表格行列，页眉页脚要么剔除、要么标记为特殊元数据。目的是让每个信息点都可追溯定位—— 合同要知道条款出自第几条、第几页，财报要知道 “净利润 32 亿” 来自哪张表、哪个财年。缺了这层，Agent 答得再自信也无法回溯，对风控、合规、法律是致命的。

第三层：按语义单元切块，并注入上下文 告别固定长度切分：同一标题下的段落归为一个 chunk，完整表格结构化为图片并与下方说明文字绑定，长表格转成按行列组织的结构化文本。每个 chunk 必须带元数据（文档 ID、页码、章节、表格编号、图片描述、版本号等）。更进一步借鉴 Anthropic 的思路，给每个 chunk 补一小段上下文说明（如 “该片段出自第三章风险因素，讨论汇率波动对海外营收的影响”），和正文一起向量化，避免检索时 “只见树木不见森林”。文本走向量索引，日期、编号等结构化字段建关键词或混合索引。

第四层：把 PDF 能力封装成工具交给 Agent 不要检索完一股脑塞进 prompt 硬啃。作者设计了一组工具：search_in_pdf 语义检索、read_page 读指定页、extract_table 抽表转 CSV/Markdown、analyze_chart 调视觉模型看图、citation 返回页码片段引用。问一个事实调一次搜索即可；问 “2022 与 2023 毛利率变化” 则规划多步：先搜不同章节，再抽对应年份报表，最后综合比较。处理过程动态、按需，而不是每次搬整份文档进上下文窗口。

最后一道防线是可追溯引用与评测闭环：回答标注每个论断来自第几页第几段；评测不能只看最终答案对不对，要拆开量化 —— 检索到的 chunk 页码对不对、表格行列值准不准、OCR 有没有漏字错字、图表有没有被正确理解。

作者最后点题：面试官真正考察的是面对非结构化数据时自底向上的工程拆解能力和 “从能跑到可靠” 的架构意识，越靠近数据入口，越考验对系统脆弱性的理解。

评论区有人提到用 docling 解析文档再 merge 表格和章节，属于同类思路的另一种工具选择，仅为单条评论提及，未形成共识。
