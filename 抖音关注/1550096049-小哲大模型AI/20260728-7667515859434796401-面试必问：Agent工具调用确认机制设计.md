这条视频是博主小哲讲的一道 Agent 开发面试题：工具调用要不要让用户确认。他的核心观点是，这题考的不是 “加不加弹窗”，而是权限边界与工作流设计—— 确认机制要按副作用、可逆性、金额、数据敏感度和外部影响分级，而不是按模型自信度分级。

为什么不能一刀切 作者指出，很多团队用一个全局开关管所有工具调用，结果低风险查询频繁打断用户，高风险操作又因为用户点惯了确认，让确认框变成摆设。Agent 一旦能调工具，就可能真的发邮件、改数据、下订单，所以关键是分清 “哪些能自动化、哪些必须被人拦住”。

四层分级（作者给出的答案模板）

只读动作：查订单、读知识库、算价格、生成草稿 —— 自动执行，但要做权限过滤和日志审计。
低风险可逆写入：创建待办、保存草稿、标记状态 —— 可自动，但必须留撤销入口。
高风险副作用：退款、扣款、发券、删数据、对外发送内容 —— 必须暂停确认，且确认框要展示工具名、关键参数、影响对象和不可逆后果。
禁止动作：直接拒绝。

两个容易被追问的细节 一是确认后要重跑校验。用户批准发券，但等待确认的几十秒里订单可能已退款、库存已变，直接执行就会出错，所以执行前要重新读取权限、库存、金额和时间窗口。二是审批结果要绑定具体 call id，恢复时只对这一次调用生效，避免 “一次批准、处处放行”。

作者还提到 OpenAI 的 Human-in-the-loop 机制：把敏感工具调用暂停成 interruption，由用户 approve 或 reject，本质是把 “模型想执行” 和 “系统允许执行” 拆成两个状态。体验层面他的建议是低风险默认自动、高风险集中确认、批量任务只确认策略和例外，并监控确认通过率与拒绝率 —— 总是无脑通过说明文案不够具体，总是拒绝说明触发规则太激进。确认记录本身也是审计证据，出纠纷时要能还原当时确认的是哪个动作、哪些参数、什么后果。

视频结尾的画面把外部副作用管控归纳为四大支柱：策略判断、参数展示、审批记录、恢复逻辑。需要说明的是，这是作者面向面试场景的方法论总结，不是某个平台的官方规范；片中提到的 OpenAI 机制属于其 SDK 的设计思路，具体接口细节建议以官方文档为准。
