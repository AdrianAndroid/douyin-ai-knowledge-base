这是「小哲」讲的一道大模型面试题：固定 8K 窗口怎么撑住 100 轮长对话。他的核心观点是，这题考的不是某个技术名词，而是资源控制能力；解法是把模型变成无状态计算单元，把记忆交给外部的分层记忆架构。

为什么不能直接堆长上下文 作者先否掉了 “窗口越大越好”：公有云 API 每轮都带全量历史，成本随轮次线性上涨；私有化部署时 KV Cache 吃显存，并发数会被压到很低。而且输入越长，预填充越慢、首字延迟（TTFT）越高；模型还容易 “中间信息丢失”、注意力被稀释产生幻觉，几十轮后出现上下文漂移、前后矛盾。所以工程上把基线定在 8K，兼顾响应速度与吞吐。

整体思路：计算与存储解耦 模型只做当前输入的推理，会话的持久化、记忆生命周期、压缩和结构化状态全部交给外部存储与调度层。核心组件是 “上下文协调器”，负责三件事：按当前提问动态分配各层 token 额度；向四层存储并发检索，把总耗时压到最慢那一次调用；对超限内容强制截断，某层超时或报错就立刻降级兜底。

8192 token 的切分

状态管理区 500：存 Redis，放用户画像、当前目标、已敲定的硬性事实，固定在提示词最前段
短期记忆 2500：最近 3—5 轮原始对话，存关系型数据库，保真度最高
中期摘要 1500：前几十轮的增量压缩摘要，后台异步生成
长期外挂 2000：向量库，按语义相似度召回早期片段
安全水位约 1700：留给模型推理和输出，不填满

四层各自的落地要点 状态区把关键事实抽成结构化 JSON（如 “零停机、副本延迟小于 5 秒”“第 12 轮否决了哈希分区”），不经模型加工，所以零语义损失，是百轮后不矛盾的底牌。短期区按先进先出溢出，溢出时同步触发两条后台流水线：生成摘要、切块向量化。摘要必须异步做，绝不能卡在主链路上；用递归增量方式把旧摘要和新溢出轮次合并，删寒暄、保数字与决策因果。长期区切片要按 “一问一答” 整块切，带轮次编号和时间戳；余弦相似度低于 0.78 宁可不召回，先取前 10% 再用重排模型精算出 2—3 个片段。

为什么是这些数字 短期压到 1500 以下，用户贴两段代码或几条日志就撑爆；放到 4000 以上又会挤占检索和状态区，几十轮后早期细节召不回来。2500 是反复测试的平衡点。500 的状态表不能省，因为摘要本质是另一个模型做的有损压缩，轮次越多语义损耗和幻觉继承越严重，只有结构化状态表能做到零损失。
