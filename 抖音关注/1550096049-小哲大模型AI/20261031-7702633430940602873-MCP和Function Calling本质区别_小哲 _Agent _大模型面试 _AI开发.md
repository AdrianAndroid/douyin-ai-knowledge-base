这条视频是博主「小哲」针对大模型面试做的知识拆解，核心结论是：MCP 和 Function Calling 不是替代关系，而是上下游协作关系—— 一个在应用层管 “工具怎么被发现和连接”，一个在 LLM 层管 “模型怎么决定调哪个工具、传什么参数”。

第一问：两者各在哪一层？ Function Calling 属于 LLM 层能力：调用模型 API 时把工具以 JSON 格式传进去，模型生成回复时输出结构化的调用参数，解决的是 “模型如何决策”。MCP 则是应用层协议，定义工具提供方如何把工具暴露给 Agent 框架，核心是发现、连接和标准化调用。作者用一句话概括：一个在 LLM 侧，一个在应用侧。

第二问：MCP 会取代函数调用吗？ 作者认为这是媒体宣传造成的误解。MCP 标准化的是工具的描述与发现 —— 一个 MCP 服务器统一工具名称、参数和返回值格式，任何支持 MCP 的框架都能自动接入；但最终仍要由 LLM 通过函数调用格式拿到工具定义。他打了个比方：函数调用是操作技能，MCP 更像工具说明书，说明书替代不了熟练的操作工。

第三问：MCP 解决了什么痛点？ 没有 MCP 时，每接一个工具都要手写定义、手工处理输入输出格式和生命周期，十个工具就是十份定义加十套适配逻辑。MCP 让工具方只实现一个服务端，把定制开发变成即插即用。但作者也点出边界：MCP 目前只解决了发现和连接，安全和权限控制尚未在协议中定义，比如 “谁能卸载工具、卸载后谁负责”，需要上层框架自己实现。

第四问：生产环境怎么协同？ 三层架构：工具层用 MCP 服务器暴露描述 → 框架层自动发现并转换成 LLM 能懂的 JSON Schema → LLM 层通过函数调用决定用哪个工具和参数 → 框架再按 MCP 协议把请求发给对应服务器。

作者最后总结面试考察的三层：认知上分清层级、关系上理解上下游、工程上能讲清落地链路并指出 MCP 的安全短板。需要说明的是，这是博主面向面试场景的讲解，其中 “MCP 尚未定义权限控制” 属于他的判断，协议本身也在持续演进。
