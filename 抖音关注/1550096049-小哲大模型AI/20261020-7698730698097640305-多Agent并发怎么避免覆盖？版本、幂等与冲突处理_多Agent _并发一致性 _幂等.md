这是「小哲大模型 AI」讲多 Agent 并发协作的一期科普，核心结论是：几百个 Agent 同时干活，不能靠一把全局锁，也不能完全放开，而要按「缩小共享范围 → 控制提交版本和副作用 → 选合适的合并机制」三步走。

先破两个常见做法

作者认为锁本身没问题，问题在锁的范围和持有时间：一个 Agent 推理很久还锁着整个任务，其他工作就被拖住；但短时间的共享状态提交锁、按资源加锁仍然合理。消息队列能排顺序，却不保证请求依据还有效 ——Agent 可能先读了旧状态，思考完才把修改送进队列，所以提交时要再检查版本。

核心方法：拆任务 + 带版本提交

把任务拆成边界清楚的部分，比如一份运营方案拆成市场分析、竞品调研、用户画像，独立部分并行，共享字段交给协调层检查。
提交时要说清「改哪个对象、基于哪个版本、想做什么改变」，而不是丢一份完整文档直接覆盖。
冲突判断分两层：先看是否改同一资源，再看有无业务冲突。改市场规模和删竞品段落可以独立处理；两个同时改同一结论，就不能只按先后顺序判对错，需要明确负责人、合并规则，或让任务基于最新信息重新生成。

文本编辑与通用业务要分开

文本协作可考虑 OT（操作转换）：一个操作在前面插入段落，另一个按旧位置删除后面内容，就要调整后者位置。但作者强调转换规则必须完整定义，不能靠「段落号加一」糊弄；两个操作删改同一内容时，旧版本操作也不能一律执行 —— 比如基于第五版、当前已到第十版，系统要检查中间历史能否安全转换，不能就拒绝提交、让任务重新计算。转账审批、库存扣减这类业务则要按各自约束处理，不能套用文本编辑的转换算法。

幂等、状态机与 CRDT 的边界

每个动作带唯一幂等标识，服务端记住已处理的请求，避免重复提交造成重复副作用；状态提交走状态机，检查当前状态是否允许该动作、允许哪些回退。版本号能检测陈旧写入，向量时钟能表达分布式事件的因果关系，但都只是识别问题，最终仍要决定合并、重试、拒绝还是人工处理。CRDT 能让副本按规定合并并最终收敛，但数据收敛不等于业务意图相容，余额、审批条件未必天然正确。

规模与瓶颈

中心协调层承担路由、版本和合并，规模上来可能成瓶颈，但阈值取决于操作频率、数据大小和实现，作者明确说不要把「一百个 Agent」当固定上限。
