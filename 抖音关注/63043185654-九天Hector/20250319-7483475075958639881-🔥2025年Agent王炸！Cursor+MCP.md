MCP 要解决的问题

大模型本身无法直接和外部工具通信，过去的做法是 Function Calling：写一个外部函数当 “中介”，一头接大模型请求，一头调外部工具，比如查天气。这套设计本身没问题，但每个工具都要单独写函数。像 Manus 这类 Agent 处理一个任务要调用几十个外部工具，就得写几十个函数，工作量极大。

MCP 的两个方案

一是统一命名：把大模型运行环境叫 MCP Client，把工具端叫 MCP Server；二是统一两者的运行规范和通信用的提示词模板。这样同一个服务器（比如查天气、网页爬取、查本地数据库）只要有人开发一次，其他人就能直接复用，不必重复编写。GitHub 上因此迅速出现了大量现成的 MCP 服务器，本地大模型支持 MCP 后，几行代码就能接入。Anthropic 还提供了支持 Python、TS、Java 等语言的 SDK，几行代码就能自己开发一个 MCP 服务器。

需要留意的一处口误

视频里把 Agent 说成 “Agent contacts protocol”，这明显是口误，MCP 的全称是 Model Context Protocol，由 Anthropic 在 2024 年 11 月提出，2025 年 2 月 Cursor 宣布支持后才真正出圈。标题里 “人人手搓 Manus” 属于博主的乐观判断，不是已发生的事实。

先抛出问题，交代 MCP 由 Anthropic 于去年 11 月提出，早期不温不火，Cursor 今年 2 月加入支持后才被推到开发者面前。

解释大模型不能直接调用外部工具，需要外部函数做中介；工具越多，要写的函数越多，Manus 一个任务就要几十个。
