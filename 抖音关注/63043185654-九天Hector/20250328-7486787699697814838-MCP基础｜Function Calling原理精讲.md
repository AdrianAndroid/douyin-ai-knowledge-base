这条视频是 九天 Hector 的 Function Calling 零基础原理讲解，核心观点是：模型本身不直接执行外部操作，而是通过 “发消息请求调用” 的方式，让外部函数去干活，再把结果交回模型组织成回答。

整体流程

作者用一张流程图说明：用户提问后，若模型开启了 Function Calling，它会先判断这个问题需不需要外部工具。需要就先去调用工具，拿到结果再回复用户；不需要就直接回答。

两个关键前提

模型必须先知道有哪些工具。作者以查天气为例：先把外部函数设计好，再用 JSON Schema 把函数功能、必填参数写清楚，每次问答时把这组描述一起输入给模型，模型才知道 “有哪些工具、各自能干什么、调用要传什么参数”。
调用动作本身是一条消息。模型不会自己执行函数，而是发出一条 function call message，里面封装好参数（比如地名），相当于告诉外部函数 “我要调用你，参数是这个”。

一次完整调用要经过两次模型响应

外部函数收到请求后立即响应，回一条 function response message，内容就是查询结果（比如北京天气）。模型收到后再对用户原始问题给出最终回答。所以整个轮回里模型响应两次：一次发调用请求，一次答用户；而外部函数必须一直在线待命，来一个请求就回一个。

作者由此点出：外部函数本质上就像一个服务器，客户端有需求就给出响应 —— 这也是理解 MCP 里 “工具 / 服务端” 角色的基础。

用户提问后，模型先思考是否需要外部工具，需要则先调用再回复，不需要则直接回答。

模型必须提前知道有哪些外部函数、各自功能与必填参数，靠 JSON Schema 在每次问答时输入给它。

以查北京天气为例，模型发出携带参数（地名）的调用消息，外部函数随即响应。

外部函数把天气结果封装成 function response message 返回，模型再据此给用户最终答复。

整个流程模型响应两次，外部函数需持续待命，本质类似一个随时响应的服务器。
