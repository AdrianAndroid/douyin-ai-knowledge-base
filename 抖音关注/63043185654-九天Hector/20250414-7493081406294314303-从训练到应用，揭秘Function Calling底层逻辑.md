这是博主九天 Hector的一期硬核技术讲解，主题是Function Calling（外部函数调用）—— 也就是让大模型能 "动手" 调用天气查询、搜索等外部工具的那套机制。作者的核心观点是：智能体（Agent）能不能干活，关键看模型原生的 Function Calling 能力，而 MCP、各种 Agent 框架本质上都是对这套流程的封装和优化。

一、为什么需要它

大模型本身只会输出文字，没法自己写代码、跑 API。而且 "该不该调工具" 要看用户意图，不能靠关键词规则。作者举了三个都带 "北京" 的问题：问推荐电影不用查天气；问出门穿多少要查北京天气；问去杭州会不会更暖，则要同时查北京和杭州。真实智能体动辄十几个甚至几十个工具，识别多重意图并匹配工具并不容易。

二、三步执行流程

把用户输入和函数说明（JSON Schema 格式，相当于函数的 "名片"，写明名称、输入输出）一起交给模型；
模型做意图识别：无关问题直接正常回答，相关则输出一条 function call message，里面是函数名和参数；
外部函数拿到参数后真正运行 API（比如把 Beijing 传进 get_weather），把结果封装成 function response message 加回对话，模型再据此给出最终回复。

作者提到，用 OpenAI 开源的 Agents-SDK 可以一行代码跑完全流程；MCP 则让开发者直接接入现成工具生态，"像搭积木"。

三、底层原理：特殊标记符 + 指令微调

模型之所以能在 "普通回答" 和 "结构化调用" 两种模式间切换，是因为训练时文本里带了 <|begin of sentence|>、<|user|>、tool_calls_begin 这类隐藏标记，用来切分和规范输出格式。DeepSeek-R1 的 <think> 也是同类标记，只是允许打印出来。能力来源是指令微调：训练数据在系统提示词里塞入虚拟工具信息，output 里给出 function call message 示例，模型就学会了这种响应模式。

四、四项优化思路

沿用训练时的系统提示模板；小尺寸模型可用对应工具的调用数据集做微调（LLaMA-Factory、千问 Agents 等工具支持）；评论区还补充了成本侧的做法 —— 工具多时先筛选相关函数、规划阶段定工具、执行阶段只调对应工具，几千个函数则拆多 Agent 处理。

评论区有个值得注意的分歧：有人称自己 2023 年写的 Java 版 MagicGPT 就是 MCP，但有回复指出 MCP 是协议标准，单个自写工具只是函数，两者不在一个层级。另外有用户反馈 R1 调 MCP 时参数会乱拼，换 ChatGPT 就正常 —— 这正对应视频说的 "原生调用能力因模型而异"。
