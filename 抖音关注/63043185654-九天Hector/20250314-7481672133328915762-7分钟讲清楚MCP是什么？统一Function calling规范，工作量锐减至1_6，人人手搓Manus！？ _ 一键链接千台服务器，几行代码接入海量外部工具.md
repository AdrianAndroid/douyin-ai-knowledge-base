这是博主九天 Hector的一期 MCP 科普视频，核心一句话：MCP 是 Agent 调用外部工具的统一协议，把原来每个工具都要手写接口的活儿，变成 “装库 + 几行代码” 就能接入。

他讲的主线

是什么：MCP 全称 Model Context Protocol（模型上下文协议），由 Claude 母公司 Anthropic 在 2024 年 11 月提出，2025 年 2 月 Cursor 宣布支持后才真正火起来。作者用 “书同文、车同轨” 打比方 —— 统一规范，协作效率自然上去。
解决什么痛点：大模型本身不能直接和外部工具通信，要靠 Function calling（OpenAI 2023 年 6 月提出）加一个 “外部函数” 当中介。问题是每个函数动辄上百行代码，还要额外写 JSON Schema 功能说明、设计提示词模板。他举了自己团队开发 MateGen 的例子：只为调用 6 个外部函数，写了 3000 多行代码；而 Manus 每处理一个任务就要调网页搜索、网页访问、沙盒文件管理、代码解释器等几十个工具，工作量可想而知。
MCP 的两个方案：一是统一命名，把大模型运行环境叫 MCP Client、外部函数运行环境叫 MCP Server；二是统一两者的运行规范和通信提示词模板。好处是通用需求（查天气、爬网页、连 MySQL）只需一个人开发一次，大家复制即用，GitHub 上已积累大量现成 Server。
接入与效果：Anthropic 提供 Python、TS、Java 等多语言 SDK，几行代码就能写 Server；Client 端不限于 Claude，也支持本地 / 在线模型和 IDE。MateGen 在 MCP 加持下，同样功能的手写代码从 3000 多行降到 500 行 —— 这正是标题 “工作量锐减至 1/6” 的来源。

需要分清的一点：视频里 “上千种 MCP 工具”“人人手搓 Manus 的时代即将到来”“2025 注定是智能体爆发的一年” 属于作者的判断和展望，不是已核实的数据结论。评论区也有争议：有人认为 MCP 本质仍是 Function calling/API 的封装，并非全新能力；也有人觉得大模型自己就能写接口，MCP 并非必需。较被认可的理解是 ——MCP 不替代 API，而是把 API / 服务打包成大模型能直接读取的统一接入层，类似 USB 接口或集装箱标准。
