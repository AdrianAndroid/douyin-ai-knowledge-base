这是九天 Hector 的一场Agent Skills 系统开发公开课，核心观点是：Skills 不是 “一个工具” 或 “一段提示词”，而是一套需要 Agent 底座配合才能跑起来的机制。

Skill 到底是什么 一个 Skill 就是一个文件夹，里面放一份 SKILL.md。文件顶部用 YAML 写 name 和 description 作为元数据，正文用自然语言写清使用场景、执行步骤、示例和注意事项。作者以 “查询天气” 为例：把这个文件夹拖进 Agent 的 skills 目录，Agent 就 “学会” 了查天气。

底层运行机制（关键） 作者拆解了拖入文件夹后发生的三步：

系统检测到新增技能，把元数据写进 system message；
用户提问时，Agent 先调用内置的 read_file 工具读取该 SKILL.md，内容以 function response 形式进入消息队列；
Agent 再发起第二轮工具调用（如 fetch 访问天气接口），拿到结果后回答。

所以 Skills 本质是基于 Function Calling 实现的动态上下文加载—— 只在需要时读文档，而不是把所有说明塞进上下文。

三个常见误解

Skills vs Function Calling vs MCP：Function Calling 是能力基础，Skills 是更高层的技能组织方式，MCP 只是工具接入的一种可选形式，Skills 并不依赖 MCP。
LangChain 支不支持 Skills：这不是框架问题。只要 Agent 有读文件工具、system prompt 能注入技能元数据并引导 “先读文档再调工具”，任何框架甚至不用框架都能实现。
Skill 通用吗：不通用。SKILL.md 里写的工具名（如 fetch_url）是特定 Agent 的，换一个 Agent 就失效，所以一套 Skill 只适配一套 Agent。

开发侧要点 作者给出最小可行方案：扫描 skills 目录生成元数据快照注入 system prompt + read_file/fetch 两个工具 + 用 LangChain 的 create_agent 组装。完整版 “复返 OpenClaw” 则加了命令行、Python、浏览器自动化、RAG 记忆、Canvas 等模块。他还提到 Anthropic 的 Cowork 发布 11 项企业技能后引发软件股大跌，用来佐证 “通用 Agent + Skills” 正在替代部分垂域定制开发 —— 作者判断这能覆盖约 80% 的普通场景，剩下 20% 的复杂场景仍需深度定制。

评论区有位广东用户点出了真正的难点：不是单点功能，而是 Skill 与工具、记忆之间的编排边界，边界控好了 Agent 才可控。
