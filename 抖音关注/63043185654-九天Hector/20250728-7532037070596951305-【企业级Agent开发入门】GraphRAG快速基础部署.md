这是一节微软 GraphRAG 快速部署与调用的实操公开课，讲师是「九天 Hector」，属于《大模型与 Agent 开发实战》12 月班体验课。核心内容是把一份 txt 文档跑成知识图谱，再用 local /global 两种模式做问答，并对比两者效果。

一、先讲清 GraphRAG 是什么

作者认为，微软 2024 年 2 月提出 GraphRAG 设想、6 月在 GitHub 开源同名项目，至今迭代到 v0.5，仍是开源实现里企业应用最广、效果最稳的一支（同期还有 nano-graphrag、light-graph 等）。它的思路是：先把文档拆成短文本，用大模型抽取实体和关系，构建知识图谱，再对实体做社区聚类、生成社区报告；查询时从图谱切入，而不是像普通 RAG 那样只做向量片段匹配。

流程分两段：indexing（索引） 一次，querying（查询） 多次。索引阶段依次是文本切分、实体提取、关系提取、社区聚类、社区报告，最终落成 entities、relationships、communities、community_reports、text_units 等 parquet 表。

二、实操步骤

pip install graphrag，建主目录（示例 openl）和其中必须叫 input 的子文件夹，放入测试文档（《ID3C4.5 决策树建模流程》，约 4400 字符）。
graphrag init --root ./openl 初始化，生成 prompts、.env、settings.yaml。
改配置：.env 填 API Key；settings.yaml 里改 LLM 模型（gpt-4o 或省钱的 gpt-4o-mini）、api_base 反向代理地址、embedding 模型（text-embedding-3-small 为 1536 维，large 为 3072 维）及其 api_base。
graphrag index --root ./openl 构建索引，结果在 output 文件夹。
查询：命令行 graphrag query --root ... --method local/global/drift --query "..."；或在 Python 里导入 query 模块，读表入缓存，构建上下文构建器 + 搜索引擎对象，search_engine.search() 反复提问。

三、一个必须知道的坑

v0.5 用 OpenAI embedding 时，lancedb.py 读取向量会因维度不匹配报错，需在第 55 行加 n=1536（large 模型则 3072），并在第 59 行把 n 作为参数传入。换开源模型同理，要先查清向量维度。

四、local 与 global 的差别（作者实测结论）

local：问题里的实体直接匹配图谱实体，再找实体背后的文本片段。快、省 token，但问题里没有图谱实体时会直接答 “无法回答”。
global：问题先匹配社区报告的 description，从社区下钻到实体和文本，还会先汇总生成一份参考文档再作答，通常调用两次模型。慢、token 多（示例输入近 3000、输出 800 多），但总结类、主观评价类问题明显更强。
drift：local 的增强版，会连带匹配实体所在社区的其他实体，性能介于两者之间，课上说放到付费课细讲。

用近 5 万字课件文档测试：“文档介绍了几种决策树算法”，local 答不出，global 准确答出 cart、ID3、C4.5、C5.0 四种；“哪个算法最有前景”“这篇文档写得怎么样” 这类问题，也只有 global 能给出有依据的评价。

另外，默认提示词模板是英文，所以中间生成的实体描述、社区报告都是英文，改成中文模板后结果也会变中文；社区数量会因大模型输出的随机性而浮动，作者这次小文档聚出 3 个社区，大文档 30 多个。

想接着看的话，可以聊 global 模式那两次模型调用具体怎么串起来，或者 lancedb 那个维度 bug 为什么非改不可。
