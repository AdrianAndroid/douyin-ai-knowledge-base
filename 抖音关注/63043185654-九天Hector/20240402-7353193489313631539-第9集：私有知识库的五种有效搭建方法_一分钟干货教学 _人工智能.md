这是博主九天 Hector「大模型热门项目」系列第五期，主题是私有知识库搭建：把本地长文档交给大模型，让它基于这些文档回答问题。作者的核心观点是，除了自己训练模型（对多数企业不现实），目前主流有 5 类技术路线，各有取舍。

五种方法及关键条件

整篇文档直接输入：文档不长时，每次提问把全文当系统消息喂给模型。优点是信息无损、不丢细节；缺点是受模型最大上下文长度限制，超长文档塞不进去。作者判断，随着上下文窗口不断放宽，这条路会越来越常用。
切分短文本 + 问题匹配：先把长文切成小段，按用户问题匹配最相关的段落再输入。灵活、成本低，但信息有损耗，很考验切分和匹配方式。
手动切分 + 检索增强：作者在这里提到 RAG（文本检索增强），并指出难点 —— 问题可能横跨多段、需要综合多处信息才能回答，只喂一段不够。他明确说这块比较复杂，留到以后讲。
借助现成框架：如 LangChain、LangChain-ChatChat（作者称其为效果较好的 RAG 框架）。切分、匹配全自动在后台跑，效率高；但流程写死、不易改动，不一定适配你的具体场景，效果需自行验证。
微调做知识灌注：通过改参数让模型 “永久记住” 新知识。听起来诱人，但门槛极高、效果不稳定，可能破坏模型原有能力甚至遗忘原生知识。作者补充，业内微调目前能稳定做到的多数是对话风格、语气、格式的调整，真正的知识灌注仍是难点。
Agent 开发工具：OpenAI 的 Assistant API 自带 knowledge retrieval（知识检索），把文档放进在线文件库即可调用 GPT 系列模型读取，支持总量约 12G、单文件小于 500M，操作傻瓜式、准确率高；代价是知识库要上云，数据隐私存疑。国内 GLM-4 也推出了在线知识库，但当时其 system API 还在内测。

一个容易混淆的点：作者说的 “五种方法” 里，第 2、3 种本质是同一思路（切分 + 匹配）的不同实现深度，第 4 种（LangChain 类框架）其实是把第 2、3 种自动化封装 —— 所以真正的分野是 “整篇直塞 / 检索增强 / 微调 / 托管式 Agent” 四条底层路线，框架只是外壳。
