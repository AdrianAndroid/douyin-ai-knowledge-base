作者的核心判断

微软 2024 年 2 月提出 GraphRAG 设想，6 月在 GitHub 开源同名项目，目前迭代到 v0.5；作者认为它仍是同类开源实现里企业应用最广、效果最稳的一个，其他如 nano-graphrag、light-graphrag 也有，但没超过它。
GraphRAG 技术链路长（切分→实体 / 关系抽取→建图→社区聚类→社区报告→检索），所以部署调用比普通 RAG 麻烦；它提供高、中、低三层 API，高层一两行代码能跑通，但想定制调优就得用底层 Python API。
整个流程对底层大模型性能依赖很重，默认只支持 OpenAI 的 GPT 和 embedding 系列；换开源模型可以，但必须掌握底层 API。

两个阶段：索引与查询

索引阶段把文档变成知识图谱，产物是一批 parquet 表：documents、text_units、entities、nodes、relationships、communities、community_reports。作者强调建完索引要先人工看一眼实体和关系抽得准不准 —— 这一步不准，后面查询怎么匹配都没用。

查询有三种模式，作者用同一份文档做了对比：

模式	匹配方式	特点
local	问题里的实体 ↔ 图谱实体，再找实体背后的文本	快、省 token，但接近普通 RAG
global	问题 ↔ 社区报告的 description，语义匹配	慢、贵，但总结类、主观评价类问题明显更强
drift	local 基础上向周边实体扩散	性能介于两者之间

实测里问 “文档总共介绍了几种决策树算法”“哪个算法最有前景”“这篇文档写得怎么样”，local 都答 “无法回答”，global 能准确给出 cart、ID3、C4.5、C5.0 四种并给出评价。

实操中的关键坑

作者特别提醒 v0.5 有个原生 bug：用 OpenAI embedding 时读取向量会报错，要改安装包里 vector_source/lancedb.py，第 55 行加 n=1536（small 模型）或 3072（large 模型），第 59 行把 n 作为参数传入。另外配置里要填 api_base 反向代理地址，且用了代理就不能再开其他网络工具。

成本上，六万字文档建一次图谱约两三美元，之后约十个问题一美元；作者建议建图用强模型、查询用小模型来平衡成本。可视化用 pyvis 在 Jupyter Notebook 里画点线图，线粗代表关系强，颜色区分社区。
