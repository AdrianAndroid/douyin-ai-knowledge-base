七种架构，各自解决什么、坑在哪

Reflection：自己写稿自己审，拆成 “写稿 — 挑错 — 定稿” 三步直线流程，治输出忽好忽坏。坑是同一个模型容易护短；作者的反常识判断是 “模型当评委挑错，往往比自己写答案更靠谱”，这也是后续所有校验机制的起点。
Tool Use → ReAct：给模型加工具调用和 “观察循环”，想一步、调一步、拿结果再想下一步。坑是一步想错就越跑越偏还狂烧 token。作者称 2026 年的真实现状是：多数 ReAct 反复调不通不是推理不行，而是模型经常脑补不存在的工具名，卡上线的是工具调用准不准。
Planning + PEV：先出显式计划清单（可改、可查、可中途叫停），把控制权从模型手里拿回数据层。坑是计划一错，执行再完美结果也错，所以生产环境必须加评估审查。作者的行业共识说法是 “没有评估器的 Agent 就是个会循环的 prompt”。
Multi-Agent：规划员、审核员、执行员分工、信息隔离，流程可分叉组网。坑是通信成本爆炸、错误传染、调试折磨；价值在 “把认知分工写进架构”，不是堆数量。
Blackboard：公共黑板 + 总调度器，谁满足条件谁干活，适合动态调度。坑是状态被谁改难以追溯。作者用 “医院分诊台只管进门一次” 对比 “黑板是全程总控台”。
Ensemble：多 Agent 并行出答案再汇总，换可信度。坑是简单投票取平均会抹掉真实分歧 ——意见不一致本身就是重要信号，要保留并解释分歧原因。
Memory：分层记忆 —— 带时间戳的情节记忆、存稳定事实的语义记忆、可做多跳推理的图记忆；关键变化是从 “相似度检索” 走向 “关系推理”。

高阶与收尾 思维树推理把控制写在代码里、模型只出候选方案；沙箱模拟先试错、审批通过再真执行；元认知系统要 “敢说我不会”。三句话总结：别迷信万能 Agent，先把状态和控制流画明白；多数项目从 ReAct 起步，上生产要校验、记忆、风险控制三样齐备；高级能力是清楚知道什么不能干。选架构别问哪个最好，问自己缺哪类控制能力。
