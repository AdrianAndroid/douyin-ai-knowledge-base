这条视频是「AgentAlpha 创客星球」讲的一道大厂 Agent 面试题：同一个模型（比如 GLM）放进 Claude Code 和 Codex 这类不同的 “壳” 里，为什么表现会差一截？ 作者的核心回答是：变的不是模型会不会，而是它能不能把会的东西稳定做对，关键在 Harness（模型外面的工程外壳）。

核心公式与判断 作者认为 Agent 的实际能力约等于「模型 × Harness × 工具 × 环境 × 反馈 × 预算」的乘积关系。他强调这只是表达 “共同约束”，不是能代入数字的量化公式。Harness 本身不提升模型的潜在推理能力，它决定的是：模型能看到什么、能做什么、收到什么反馈、上下文怎么接续、一次动作的副作用半径有多大。

两个类比讲清机制

同一师傅，两种工位：糟糕的 Harness 只给一把 “万能扳手”（无限制 Shell 权限）和嘈杂广播（不可读的终端反馈）；优秀的 Harness 给清晰图纸、分区专用工具、测量仪表、验收单和受控电闸，对应 Agent 与计算机之间的接口设计。
同一个 Bug，两种结局：差环境里模型面对庞大代码库只能全量扫描、盲改，收到乱码报错后反复重试陷入死循环，还可能误删无关配置；好环境里是 “模型提工具调用 → Harness 执行 → 返回短而可读的 observation → 模型迭代”，直到证据达标或转人工。关键是 可验证反馈—— 静态分析、真实页面、运行结果都算，反馈不可靠时 Agent 只是在盲目生成文本。

两个容易踩的误区

工具越多、权限越大越强？ 作者明确否定。权限越大不等于能力越强，目录访问、网络连接、敏感操作都必须隔离或审批，否则噪声和破坏风险同步上升。好 Harness 懂得做减法。
长任务靠压缩上下文？ 压缩不是无损记忆，关键信息一丢模型就偏航。工程做法是把验收条件、当前状态、产物、Git 基线持久化，每个会话只推进一个可验证的增量，中断后靠状态文件续上。

最后他提醒：比较两个 Harness 必须控制变量，固定模型、任务、工具集、上下文成本和权限，别把壳带来的分数变化算成模型升级。
