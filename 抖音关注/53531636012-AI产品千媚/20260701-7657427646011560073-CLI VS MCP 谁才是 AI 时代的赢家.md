这条视频是「AI 产品千媚」做的科普讲解，核心结论是：CLI 会吃掉 MCP 的一部分场景，但替代不了它，两者底层都是 API，只是给 AI 用的两种不同 “外壳”。

主线：界面变了，是因为使用者变了

作者用一条演进线串起整条逻辑：早期打孔卡片排队等机器，人没法实时指挥；终端出现后敲一行回一行，这就是 CLI（命令行界面），比如 git commit 修复bug，命令名、子命令、参数三段式。但 CLI 要求你会说机器的话，命令、参数、路径都得记。于是有了 GUI（图形界面），把 “记命令” 换成 “认图标”，普通人才能用。可 GUI 只服务一双手一双眼睛，自动化差，程序也读不懂那些花花绿绿的图形，于是有了 API—— 软件和软件直接对话，比如美团通过 API 问微信 “这笔钱扣了吗”。

为什么不让 AI 直接点界面或直接调 API

让 AI 点 GUI 等于让它用最弱的腿走路：AI 强在读写文字，不强在截图找按钮猜位置，中间弹个窗、点歪一下就断链，还慢、还烧 token。
直接调 API 理论可行但很痛苦：每个接口长得不一样，调哪个、填什么参数、权限怎么处理、返回怎么解析都得提前写死，像做饭不给厨房、只给一摞燃气阀和水管说明书。

作者总结 API 对 AI 的三个问题：不会自我介绍、各家不统一、太底层。

MCP 解决了什么

MCP（模型上下文协议） 相当于给 AI 和工具之间定了 USB 式统一插口，带来三个变化：工具会自我介绍（“我叫 read_document，需要给我一个 document_id”）、AI 能当场发现能力而不用写死在代码里、调用方式统一。所以 API 是给程序调的，MCP 是给 AI 发现和调用工具的。

CLI 又回来干什么

当任务不是调一个工具，而是一串工具连起来（读文档→整理→写文件→发消息），MCP 每步都要选工具、填参数、等返回，链路长。CLI 更像一本说明书挂着一堆子命令，靠 skill 告诉 AI 每条命令怎么写，命令背后自动处理请求头、URL、返回解析。好处是省上下文（用到哪个能力再翻对应 skill）、好组合成流水线。作者的比喻：MCP 像工具柜，强在发现工具；CLI 像流水线，强在编排工具。

结论与建议

本地自动化、批量处理场景，CLI 很强；远程服务、消费级 AI、企业权限管理，MCP 更合适，因为不依赖终端、边界清晰、权限好控。
做 AI 产品别纠结外壳，先把 API 做干净、能力说明写清楚—— 外壳会越来越容易生成，值钱的是这两样。评论区最高赞也认同这点，说 “干净的 API 和清晰的描述命令是 agent 的脚手架”。

一个容易误解的点：视频里说的 CLI 不是 “老式命令行”，而是把工具能力封装成命令行 + skill 说明书，专门给 AI 读和编排用的形态，和传统给人敲的 CLI 目的不同。
