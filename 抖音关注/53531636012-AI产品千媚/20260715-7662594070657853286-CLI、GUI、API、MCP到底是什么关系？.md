# CLI、GUI、API、MCP到底是什么关系？

CLI、GUI、API 和 MCP 本质上是同一套底层能力针对不同使用者的不同封装形式。回顾工具交互方式的演变历程，能帮助我们更清晰地理解它们在 AI 时代的定位与关系。

00:00
引出四大核心概念
在日常使用 AI 助手连接各类办公软件时，经常会遇到 MCP、CLI、API 和 GUI 等不同的接入方式。这些词汇常常让人感到困惑，不清楚它们之间的具体区别以及应该如何选择。实际上，它们代表了人机交互和程序对接的不同发展阶段，本质上都是为了实现同一套底层能力，只是针对不同使用者进行了不同形式的封装。

00:30
CLI：用文字指挥机器
在早期机房批处理时代，人们无法实时指挥机器，直到终端的出现才解决了这一问题。CLI（命令行界面）允许用户通过敲入一行行文字命令，让机器实时给出反馈。例如，通过特定的命令指令，可以直接让飞书向指定群聊发送通知消息。CLI 主要服务于会写命令的人和自动化脚本，它赋予了人实时控制机器的能力，但由于需要记忆具体的命令、参数和路径，对普通用户而言存在较高的技术门槛。

01:09
GUI：普通人的交互界面
为了让更多人能够使用软件，GUI（图形用户界面）应运而生。它将复杂的文字命令转化为直观的图标、按钮和输入框，用户只需通过点击和打字即可完成操作。比如给飞书发消息，只需找到对应群聊并在输入框中打字发送即可。GUI 极大地降低了使用门槛，解决了普通人如何更容易使用软件的问题。然而，GUI 是为人眼操作设计的，当需要实现程序与程序之间的自动化对接时，GUI 就显得无能为力了。

01:38
API：程序之间的对接标准
当系统产生一笔大额订单，需要自动通过飞书推送消息通知时，程序之间无法依赖 GUI 进行交互，必须使用 API（应用程序接口）来调用。如果说 CLI 服务的是会写命令的人，GUI 服务的是普通用户，那么 API 就是专门服务于程序的。每一代工具封装方式的变化，本质上都是因为使用者的主体发生了改变。

01:57
MCP：AI时代的工具封装
随着 AI 的到来，如何让大模型高效使用现有工具成为了新的课题。如果让 AI 去操作 GUI，它需要像人类一样看屏幕、识别按钮并模拟点击，一旦页面布局变动或加载缓慢，整个过程就会变得极不稳定。而如果让 AI 直接调用底层 API，虽然理论上可行，但由于 API 涉及复杂的接口文档、群 ID、令牌传递以及结果解析，对 AI 而言过于底层且繁琐。

为了解决这一矛盾，MCP（Model Context Protocol）出现了。它相当于把 API 重新包装成了 AI 更容易理解和调用的工具。例如，飞书的 MCP 会直接向 AI 暴露诸如 readmessage 或 sendmessage 等工具及其所需参数。AI 接上 MCP 后，就能清晰地知道自己可以调用哪些工具，因此 MCP 也被形象地称为 “AI 时代的 USB-C”。

03:05
CLI：编排复杂任务流水线
既然有了 MCP，为什么 CLI 又重新受到关注？因为很多实际任务并非单一工具调用就能完成，而是需要一长串的动作串联。例如，让 AI 提炼群聊讨论并创建复盘日程，背后至少包含了读取消息、提炼待办、创建日程、发送结果等五个步骤。如果用 MCP 来解决，需要 AI 一个工具接一个工具地调用，不仅速度慢，还会消耗大量的 Token。

CLI 则走了另一条路。它不强调单个工具，而是像一本命令说明书，将一系列复杂的操作步骤拼装成一个命令去执行。每个命令背后会自动替 AI 处理 API 调用、令牌传递、网址拼接和结果解析，从而将 AI 的工作编排成一条高效的任务流水线。在这个体系中，Skill 扮演着 CLI 的说明书角色，负责告诉 AI 在什么场景下使用哪条命令，实现了 “命令负责干活，Skill 负责教 AI 怎么干活” 的高效协作。

04:30
如何选择MCP与CLI
当一个应用同时具备 MCP 和 CLI 两种接入方式时，选择取决于 Agent 的部署形态。如果接入的是本地 Agent（如个人使用的场景），优先选择 CLI，因为它支持自动化批处理，执行效率更高。相反，如果接入的是云端 Agent 或企业级 Agent，则应优先选择 MCP，因为 MCP 不依赖特定的终端环境，并且在网络传输和权限管理上提供了更高的安全性。
