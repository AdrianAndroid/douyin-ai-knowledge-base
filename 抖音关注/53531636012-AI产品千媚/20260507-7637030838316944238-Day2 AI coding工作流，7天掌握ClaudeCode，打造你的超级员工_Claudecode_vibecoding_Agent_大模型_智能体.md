这是「7 天掌握 Claude Code」系列的第 2 天，主题是给 AI “员工” 立规矩：从 “一句话派活” 转向 “先探索、再规划、后编码、最后提交” 的完整开发流程。作者认为，第一次让 Claude Code 开发用户管理系统时，5 分钟就写完了，但风格和功能都不对，问题不在模型能力，而在工作方法。

四步开发闭环

探索：先看现有代码怎么组织，类似功能放在哪个文件，数据库怎么操作，API 怎么调用，权限系统怎么复用。
规划：列清要做什么、现有功能是什么样、新增功能是什么、用什么设计风格、要改哪些文件。
编码：按计划逐步实现，先核心功能再扩展功能，遇到问题随时调整。
提交：自查代码、跑测试、写清提交信息。

关键工具：Plan 模式

作者重点讲了 Claude Code 的 Plan 模式：它只能读文件、不能改代码。切换后提同样的需求，它会先探索项目现有模式，遇到需求不清晰的地方通过 ask user 工具向你澄清，再列出需求文档、设计方案、技术方案等详细计划，等你批准后才切到编辑模式执行。

适用边界作者也给了：改按钮、改文案这类明确小操作不需要；新功能开发、跨模块多文件、架构调整、不熟悉的新任务适合用。作者还分享了自己的特殊用法：改了很多次都没改对的 bug，先用 Plan 模式定位原因再动手，准确率会高很多。

编码阶段三个技巧

明确成功标准：别说 “做个某某功能”，要说清做到什么程度算成功，否则细节容易漏。
小步迭代：别一上来就做复杂功能再验收，从 MVP 开始，保证每一步质量。
代码审查：三个命令各有分工 ——review 快、成本低、本地运行，适合日常频繁用；ultra review 让 Claude Code 当编排器，启动多个 agent 从逻辑正确性、安全性、性能等不同视角审同一份代码，但作者提醒，用国产大模型组合或未订阅 Pro/Max 时用不了，且订阅后每账号可能只有几次免费额度，之后按量付费；security review 专注安全审查。

作者把这一阶段的核心原则概括为：从 vibe coding 转向 spec coding。

提交阶段两个命令

commit：相当于 “保存按钮”，背后依次执行查看状态、查看变更、看最近提交记录、生成 message、添加文件、提交、确认状态七步，适合改动想存到本地但还不推远程时用。
commit push pr：一键从提交走到创建 PR，自动生成 PR 描述告诉维护者改了什么，审核通过后合并到主分支发布。
