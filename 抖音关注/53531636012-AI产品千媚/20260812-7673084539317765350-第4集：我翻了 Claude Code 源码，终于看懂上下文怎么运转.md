这条视频是博主「AI 产品千媚」对 Claude Code 上下文管理机制的源码拆解。她用一个真实任务做例子：让 Claude 去 Claude Code 源码里搜和 context 相关的代码，研究它自己怎么管上下文。因为要反复 grep、读文件，工具结果越积越多，正好演示了上下文是怎么一轮轮变大、又怎么被压缩的。

核心结论：你看到的只是聊天框里的一句话，Claude Code 真正送进模型的是整个任务现场—— 系统提示词、Git 快照、CLAUDE.md、工具定义、历史 thinking 和工具结果全都在里面。所以 “没聊几句就满了”，是因为窗口里装的不只是对话。

一次请求怎么进模型：三条通道 ——system（系统提示词 + 当前分支、工作区改动、最近提交等 Git 快照）、message（用户规则、日期、记忆配置等前置 meta，加上 CLAUDE.md 和你发的话）、tool definitions（这轮能调哪些工具、参数结构）。模型每轮产出 thinking、可见文本和 tool_use，工具返回的路径、文件内容、代码片段作为 tool_result 一起带回下一轮，消息流就这样滚大。

五层压缩，按顺序层层过滤：

工具结果预算：grep、bash 这类超大输出存到磁盘，消息里只留预览和路径，需要时再按路径读回。
Snip：裁掉部分旧历史，留一个裁切标记。
Micro Compact：清掉旧的 tool_result 长输出，但保留 “调用过什么” 的轨迹。
Collapse：把旧历史折叠成局部摘要，保留分阶段进展。
Auto Compact：最后才整段重写，单独发起一次不能调工具的摘要请求，保留用户请求、关键判断、读写过的文件、错误修复、进度和待办。

作者特别提醒：这五层不是每次都走完，snip、collapse、micro compact 是否启用要看版本和运行环境。压缩后会恢复最近文件、plan、skill、agent 状态和工具变化；最终 message 被重构为「compact boundary 标记 + 结构化 summary + 尾部最近消息原文 + 恢复的动态信息」。

一个容易误解的点：压缩不是 “删掉聊天记录”，记录仍完整存在磁盘上，被取舍的只是下一次行动前模型该看到什么—— 窗口大小决定能放多少，上下文管理决定该放什么。

评论区里作者也坦白，Claude Code 源码体量大到自己看不懂，是让 AI 读完后整理成文档再拆的，所以这期更像 “借 AI 读源码” 的二手解读，具体实现细节以官方版本为准。想接着看的话，可以聊聊她那五层里最容易被忽略的 Micro Compact 和 Collapse 到底差在哪。
