开发一个 Agent 的第一步不是直接写代码，而是选择合适的开源技术框架。随着大模型及其应用需求的发展，Agent 开发架构经历了从基础组件到复杂执行系统的演进，理解这些阶段的差异是进行技术选型的关键。

回顾 Agent 开发架构的演进历程，大体可以分为三个层次，它们并非互相淘汰，而是不同层次的技术抽象：

00:00
梳理Agent开发架构演进
早期的 Agent 开发需要开发者自行处理模型调用、工具接入和结果返回等繁琐的基础工作。为了降低成本，LangChain 和 LlamaIndex 等框架应运而生，它们将这些基础能力进行封装，极大地简化了早期 Agent 的搭建流程。

随着任务复杂度的增加，仅仅连接模型和工具已显不足。开发者需要控制任务的执行顺序、保存执行状态，并处理中断与人工确认。这催生了以 LangGraph 为代表的 Runtime 阶段，其核心是让 Agent 的执行过程变得可管理和可恢复。

如今，模型推理和工具调用能力的提升让 Agent 能够自主规划步骤，但也带来了上下文管理、中间状态存储和停止条件等新工程难题。现代的 Harness 整合了前两者的能力，提供了一套高度抽象的执行系统，使开发者可以直接复用而无需从零开始搭建。

05:10
盘点主流Agent Harness项目
目前市面上的 Harness 项目繁多，根据其主要服务的场景，大致可分为以下三类：

综合任务类：不局限于特定业务，适用于研究数据、分析文档及处理代码等复杂任务。典型代表包括 Claude Agent SDK 和 Deep Agents。
编码开发类：围绕软件开发场景设计，重点支持代码理解、文件修改、命令执行及测试验证。代表项目有 Pi、OpenCode 以及 Codex CLI。
个人助手类：更关注长期记忆、多渠道交互、定时任务等能力，旨在持续为用户提供服务。代表项目如 OpenClaw 和 Hermes Agent。

此外，DeepSeek Harness 采用了高度插件化的设计理念，通过组合不同模块即可搭建出不同类型的 Agent。需要注意的是，这些分类并非绝对的功能边界，现代 Harness 的能力正在不断趋同，主要区别在于默认提供的工具集和针对特定任务的优化程度。

06:35
解析综合任务类Harness
综合任务类的 Harness 通常提供较为完整的执行系统，但在设计思路上存在明显差异。以 Claude Agent SDK 为例，它本质上是将一套成熟的 Harness 进行了深度封装，为开发者提供了开箱即用的执行环境。

在这种高度封装的模式下，系统已经内置了 Agent Loop、工具发现与调用、Session 管理以及子 Agent 执行等核心机制。开发者主要通过配置 Hook、自定义工具或补充系统提示词来干预 Agent 的行为。这种方式极大地降低了开发门槛，但也意味着开发者无法轻易将底层的核心实现替换为其他机制，牺牲了一定的灵活性。

对比其他代表项目设计
除了综合任务类，其他代表项目也各有侧重。例如，Deep Agents 同样致力于提供完整的 Harness 能力，但其设计可能更偏向于允许开发者对执行循环进行更细粒度的干预或替换。

在编码开发领域，Pi 不仅提供了强大的代码理解与执行工具，还允许开发者通过插件、SDK 甚至源码改造等不同层级的方式进行定制，以满足从简单脚本到复杂 IDE 环境的多样化需求。而像 OpenClaw 这样的个人助手项目，则超越了单纯的 Harness 范畴，演变成了一套包含消息接入和任务调度的完整 Agent 系统。

20:43
总结Agent选型核心思路
面对众多的开发框架和 Harness 系统，选型的核心在于明确业务需求的复杂度以及开发者需要对系统掌控的程度。

如果业务逻辑简单且流程固定，直接使用轻量级的 Framework 或 Runtime 进行组装依然是高效的选择。但如果面对的是需要高度自主规划的复杂任务，直接复用成熟的 Harness 可以避免从零开始搭建底层的执行循环和上下文管理。同时，开发者需要权衡 “开箱即用” 的便利性与 “深度定制” 的灵活性，选择最契合自身业务起点的技术栈。
