这条视频是 AI 产品博主「AI 产品千媚」对 CLI 与 MCP 之争的拆解，核心结论是：两者不是替代关系，而是分层分工——CLI 是主操作面，MCP 是给没有 shell 的 agent host 留的接入入口，真正的地基是 API。

作者的核心论证

“MCP 贵 32 倍” 这个说法有前提。 Scalekit 的公开测试里，同一模型、同一仓库、同一个问题（“这仓库用什么语言写的”），MCP 消耗的 Token 是 CLI 的 32 倍。作者解释原因：那次把 GitHub MCP 的 43 个 tool schema 一次性全塞进上下文，模型读了一堆无关说明；如果只注册 4 个 tool，成本就完全不是一回事。所以差距来自 “一次性全量暴露”，不是 MCP 本身的原罪。

以飞书为例，工具是三层结构。 最上层是 CLI 快捷命令（约 370 个 shortcut，参数默认值都填好，覆盖查日程、发消息、建文档这类高频动作）；不够用时下到 API command（约 225 条，参数由 agent 明确传）；再不够才直连原始 OpenAPI（2500 多个接口）。三层不是重复能力，而是 “简化入口 — 精确入口 — 兜底”。

Skill 是编排层，不属于任何一方。 飞书有 27 个 skill，它们不执行命令，而是一份 “任务说明书”，告诉 agent 什么场景用哪组工具、需要哪些权限、先后顺序和异常怎么处理。比如 “总结产品群讨论并发回群里” 这个任务，agent 先读 skill，才知道要先找 chat id、再拉消息、再建日程、再发消息，而不是一开始就把几百个命令全读一遍。

MCP 的机制是 “看卡选卡”。 飞书 MCP 目录有 1300 多个工具，但服务启动只默认加载 19 个，否则光工具介绍就把上下文撑爆。agent host 先通过 tool list 拿到这几张 tool 卡（名字、参数、说明、schema），模型看卡、选卡、填参数，再 call MCP server 去调 API。

作者的取舍判断

CLI 优势：命令可拼装、一次执行多个，效率高；但权限开得大，风险也高。
MCP 优势：一次一个工具调用，效率低些，但权限收得更紧、更安全，且不受本地 shell 限制，任何 agent 都能接入。
结论：以 CLI 为主、MCP 为接入层，底层共同维护一套 API 和能力定义；核心思维是渐进式分层，别一股脑把所有信息丢给 agent。

评论区里也有观众把 CLI 理解成 “命令工具”、MCP 理解成 “封装多个 API 的工具”，作者回复纠正说 CLI 本身是调用 API 的本地程序，本地软件如 Git 的 CLI 与 API 关系不大 —— 这属于评论区的补充讨论，不是视频正文观点。
