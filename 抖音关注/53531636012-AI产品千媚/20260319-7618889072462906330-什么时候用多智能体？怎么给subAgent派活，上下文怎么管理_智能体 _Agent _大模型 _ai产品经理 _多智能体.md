这是「AI 产品千媚」的《多 Agent 架构设计（二）》，副标题为 “Anthropic + Google 工程实践总结”，属于 “零基础转型 Agent 产品经理” 系列第七期。视频用 “第一次当老板怎么给员工派活” 作比喻，回答三个问题：什么时候该用多 Agent、怎么给子 Agent 派活、主子 Agent 的上下文怎么管理。

多 Agent 架构的核心结论是：不是越复杂越好。一个设计良好的单 Agent 配合改进的提示词，往往能达到同样甚至更好的效果；多 Agent 只在单 Agent 无法克服的特定限制下才有价值。

一、三个值得上多 Agent 的场景（Anthropic 经验）

上下文保护：子任务会产生大量信息、但大部分与主任务无关时。例如智能客服查订单，系统会返回订单详情、历史购买、物流、支付等大量内容，污染工作记忆、让推理质量下降。此时交给 “订单查询子 Agent” 处理，只回传 50—100 个 token 的摘要，主 Agent 保持清爽。前提是子任务标准明确、不依赖复杂上下文就知道该提取什么。
并行化：任务能拆成互不相关的子任务时。比如研究 “气候变化对全球经济的影响”，可同时从农业、能源、房地产几个角度并行推进，Deep Research 是典型场景。收益不只是快，更是分析更全面；代价是总计算量上升，token 成本约为单 Agent 的 3—10 倍，所以作者提醒 “杀鸡不要用牛刀”。
专业化：分三个维度 —— 工具专业化（工具跨太多不相关领域难以选择）、提示词专业化（客服要共情耐心，代码审查要精确批判，一个 Agent 难兼顾冲突的行为模式）、领域专业化（法律、医学等需要深度领域上下文）。

二、怎么派活：按上下文边界拆，不按问题类型拆 这是作者认为多 Agent 架构中最重要的决策。反例是按开发阶段拆成产品、开发、测试三个 Agent：开发不知道设计缘由，测试不知道开发做了哪些权衡，像传话游戏，每传一次信息就失真一次，为保真就得烧大量 token 做协调，协调成本可能超过工作本身。有效边界是：按功能模块（用户认证、支付）、按数据源（数据库、API、文件）、按系统（前端、后端）、按独立研究方向。反例还包括按技能拆（写代码 / 写文档）、按步骤拆，这些步骤间都有依赖，只增加协调开销。

三、上下文管理：Google Agent SDK 的四层结构

Working Context：每次模型调用时临时拼装的系统指令、Agent 身份、工具输出、记忆与文件引用，用完不存储。
Session：记录交互日志，压缩后拼装进工作上下文。
Memory：存长期可检索的知识，如主 Agent 的任务规划，即使上下文超限也不会因截断丢失，还能存长任务的阶段性总结。
Artifacts（Files）：子 Agent 输出太大时存成外部文件，只返回轻量引用，主 Agent 按需渐进式加载。作者提到像 Open Claude 这类产品记忆本身就用 markdown 文件存，记忆和文件可合并。

四、可上手的开源参考 作者推荐 LangChain 团队的Open Deep Research（基于 LangGraph 的多智能体架构，官方认证复刻 Anthropic 架构）：先进入需求澄清节点，再进入写作 / 研究节点（内部是嵌套的独立多智能体循环，supervisor 按需调工具、用 ReAct 循环），最后进入生成节点整合内容与信息源。作者自评体验不错，卡点是最后生成环节很慢，因为要汇总的内容太多，暂未想到优化方案，也在向观众征集思路。
