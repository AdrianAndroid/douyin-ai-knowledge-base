这是一期对 Anthropic 开源电商 Agent 方案的实测拆解，作者是 AI 产品博主「AI 产品千媚」。她的核心判断是：电商 AI 的难点不在 “会回答”，而在业务太复杂 —— 商品、库存、价格、订单各有规则，所以业务越复杂，越要把模型、工具和权限的边界划清楚，让 Agent 能在规则内把事办成。

作者先抛出痛点：多数电商 AI 只做到回答商品问题，而真实需求是连续的 —— 问完商品要比较、加购、查退货；运营发现缺货要出补货方案再走审批。这些环节背后都是各自的业务系统。

官方提供模拟商店做体验。导购助手干两件事：买前帮挑、买后帮查。演示里 “250 美元以内、适合全家露营的帐篷” 给出商品卡片，接着做参数对比卡片；中途突然问 “不合适能退吗” 也能查退货政策；说 “把第一款加购” 能理解指代并完成加购。更复杂的 “800 美元布置办公室” 需要自己拆成桌子、椅子、照明、收纳等需求并控总预算，还支持记住用户情况做后续推荐。操作边界只到加购，下单支付仍需本人完成。

经营助手以侧边栏形式嵌在运营后台。可以问 “最近两周销售数据有什么变化、主要由哪些品类带来”，让它分析定位问题、给降价促销建议，或做日常巡查汇总库存与订单异常。关键细节：让它出补货方案时会触发人工审批，在聊天里说 “同意” 不会执行，必须从指定审批入口确认 —— 因为补错库存、改错价格会直接造成损失。

作者认为最值得看的设计是：连续任务由一个主 Agent 承接，Skill 按需提供业务方法。市面上常见做法是一个场景一个 Agent（推荐一个、售后一个、复购一个），但用户需求是连着的，频繁交接要反复传预算、偏好、商品和购物车信息，既增加开销也容易丢上下文；售后本身还同时涉及订单、商品和政策，边界切不干净。所以该项目按服务对象只给两个 Agent（消费者、商家），各有自己的提示词、Skill 和工具，底层复用同一套执行机制和数据。新增业务也不用再造 Agent，扩一个 Skill 即可（如积分兑换）。

传统业务与大模型结合最大的问题是边界切分：搜索排序、库存价格、促销系统已积累大量规则，不该由模型重做。官方给了零售、旅游、通信、票务、娱乐四类示例，同一套思路、规则各异（零售选规格、酒店看日期天数、票务有实名）。落地只做三件事：前端入口、业务接口接入、与企业账号权限打通。运行方式三种，其中托管到 Anthropic 服务器的 Managed Agents 对国内业务基本不适用，可直接用 Messages API 版改造成自己的产品。

自有商城和后台的企业自主性最高，重点在接口打通 ——“接口本身都不确定，换再强的模型也没用”；用第三方商城和后台的，要看平台开放了哪些接口，没操作接口就先接查询和建议；商城第三方但自有运营后台的，可以先接运营助手做分析出方案。作者最后总结：这套方案的价值是区分了传统业务系统与 AI 系统的边界，用 Agent + Skill 化解业务复杂度，并把权限控制融进去，做到可校验、可监控、可追责。

评论区补充了两点工程经验：一是 master-sub 多 Agent 与 Skill 模式的选型，作者认为前者更适合调研类场景，有观众补充关键看上下文窗口是否够用、是否出现回忆混淆，Skill 模式 token 开销更可控；二是落地卡点往往不在模型，而在 ERP、审批系统的接口打通、权限划分和数据治理。
