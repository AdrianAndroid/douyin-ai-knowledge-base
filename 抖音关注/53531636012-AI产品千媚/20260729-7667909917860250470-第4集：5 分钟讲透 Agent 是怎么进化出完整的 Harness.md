这条视频来自「AI 产品千媚」，核心观点是：Agent Harness 不是一开始设计出来的，而是 Agent 进入真实生产环境后，被一个个实际错误 “逼” 出来的。作者用 coding agent 加登录功能这条主线，把 Harness 的每一层都对应到一个具体缺口。

起点：最小 Agent Loop 用户给目标 → 模型思考下一步 → 选工具 → 工具返回结果 → 模型再判断，循环到任务完成。这就是常说的 ReAct 循环，几十行 while 就能写出来。

之后逐层 “长” 出来的部分

工具层：模型不知道项目用什么框架、目录怎么组织、数据放哪，于是补上 read、search、edit、bash、browser 等工具。工具一多，就要解决 “什么时候用哪个、参数怎么传” 的问题，否则模型会用错、瞎填。
执行环境与沙箱：agent 越能干越危险，bash 能删文件、装未知依赖、读环境变量。于是给它独立工作区、限定目录、限制网络和资源、藏起密钥；多个 agent 并行还要隔离，避免 “赛博浆糊”。作者强调这层不是提高智商，而是控制犯错后的爆炸半径。
上下文管理：读几十个文件、几万行日志全塞进上下文，模型就成了 “垃圾桶”。要区分哪些规则必须常驻、哪些结果只需摘要、哪些历史可压缩、哪些结论要写进计划。
任务状态与编排：任务变长、会话中断、子任务失败、多 agent 协作，都需要外部状态机记录计划、改动文件、测试结果和下一步，从检查点续跑而不是重读仓库。
可观察性：留下结构化 trace，记录每次调用的上下文、工具、参数、返回、重试次数、耗时和 token，才能定位从哪一步开始偏离。
验证层：能看见过程不等于结果正确。agent 说 “测试了”，网页按钮点了却没反应 —— 工具给行动力，验证才给纠错能力。
治理层：能读客户数据、发邮件、改代码，就要像管员工一样管权限。

一句话收尾：Harness 不负责制造聪明，负责接住聪明产生的后果。评论区也有个常见概括 ——“agent = model + harness”，属于网友的技术语境总结，不是视频原话；另有讨论认为 Codex、Claude Code 这类工具链更贴近人们口中的 harness。
