这条视频是博主「AI 产品千媚」对 Palantir Ontology 的拆解，核心观点是：值得学的不是照着 Object、Property、Link 搭一套语义层，而是它把企业决策拆成 Data、Logic、Action、Security 四段的方法论。

四段拆解（用库存案例讲透）

Data：不是把几张表拼起来，而是把系统数据翻译成业务世界。Object 是 “这是什么东西”，Property 是 “它有什么特征、什么状态”，Link 是 “它和其他东西什么关系”。订单、商品各是一类 Object，订单包含商品就是 Link。
Logic：光看懂事实不够，还得能判断。规则是 “明天可承诺 = 实物库存 − 已预留 − 质检中 + 明天前能到”，100−20−10+0=70，客户要 80 就不能承诺。
Action：AI 只回答 “可以” 仍是问答系统，真正锁住 60 件库存才是改变业务状态，锁库存、退款都属 Action。
Security：60 件可自动锁、6000 件要人工确认、10 万元不该把权限交给 AI—— 权限边界本身就是业务逻辑，不是事后补的配置。

关键背景：Palantir 的 Ontology 诞生在大模型之前，机器理解力弱，所以业务概念、关系、规则必须提前显式定义。今天有了大模型和 Agent，不必用同样方式实现。作者认为过去系统割裂没出问题，是因为中间有 “人” 兜底 —— 老供应链负责人知道哪个是实物库存、哪个是在途，这些经验散在人脑、Excel 和部门规则里；现在 Agent 要接手判断，这些隐性知识必须变成它能拿到的 context。

落地建议：只有一个 Agent、一个场景时，先用 MCP、Skill 把业务跑起来，别为 Ontology 提前设计；等客服和销售 Agent 对 order 定义不一致、多个 Skill 重复写退款规则、多个 Agent 各自封装锁库存工具时，再把重复的沉淀成公共概念、公共代码和公共 business action。即 “先做 Agent，让 Ontology 随复杂度长出来”，而非先建模再开发。

评论区有个值得注意的纠正：最高赞认为 Palantir Foundry 更像先有平台化产品、再靠 FDE 实施适配企业场景，和视频说的 “从场景出发” 不是对立路线，而是阶段与适配方式的差别；也有人主张高准确度场景仍需确定性代码加语义层，别全押黑盒 Agent。
