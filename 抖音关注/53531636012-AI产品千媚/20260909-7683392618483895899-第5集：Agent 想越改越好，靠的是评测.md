这条视频是 AI 产品千媚 做的 Agent 评测科普，核心观点是：Agent 能不能越改越好，靠的不是 Demo 惊艳，而是评测驱动迭代。作者把 Anthropic 今年 1 月的 Agent 评测文章和阿里技术团队的评测体系工程实践放在一起讲，最后给出一张评测指标地图。

为什么 Agent 评测和传统大模型不一样 传统大模型评测只看最终回答准不准、有没有幻觉。Agent 要理解需求、排步骤、调工具、读结果、改文件，错误可能出现在执行链路任何一环 —— 订单找错、金额传错，后面工具调用再顺利也是错的。所以评测必须覆盖一次完整任务：说了什么、做了什么、系统最终变成什么状态。

三层评测框架：outcome /trace/experience

outcome（事情做成没）：作者特别区分 output 和 outcome。Agent 说 “退款成功” 只是 output，系统里真有一笔状态为成功的退款记录才是 outcome。任务完成率是端到端评测的北极星指标。
trace（过程有没有问题）：相当于 Agent 的行车记录仪，记录调了什么工具、传了什么参数、返回什么、每步耗时。阿里那篇把它拆成感知（意图理解对没）、规划（路径选对没）、记忆（多轮后还记不记得）、工具（选对、传对、调通没）四个模块。底层原则是评测体系要和 Agent 架构同构，指标掉了才知道该改提示词、工具描述还是记忆。
experience（体验和成本）：简单查询让用户等半分钟、一个问题调几十次模型烧大量 token，完成率再好也没法用。所以要加模型调用次数、输入输出 token、端到端延时等维度。

评测体系怎么搭 Anthropic 给了三个层级：task（一道题，写清输入、初始条件、成功标准）、suite（一套试卷，按业务或能力分组）、harness（把发任务、备环境、存记录、调评分器、汇总结果串起来的运行框架）；同一道题每跑一次叫 trial。作者建议早期别追求大数据集，先从真实日志、用户反馈、线上失败里挑 20—50 条代表性任务建基线，覆盖核心任务、真实用户任务、历史 bad case、边界 case 四类，再按基础技能、知识问答、多轮对话、异常输入、工具调用、多意图、模糊意图、长对话衰减八类打标做专项评测。建用例有三个坑：数据要来自真实任务、正例反例都要有（否则 Agent 会学会 “遇事就搜”）、用例要写全初始状态和成功条件。

评分器：代码 → 模型 → 人工 代码评分最便宜稳定，查参数、订单金额、状态、耗时；语义类问题用 LLM as a judge，作者强调四个原则：单一职责（一个 prompt 只评一个指标）、先推理后判断、负例引导、结构化输出。人工负责专业判断和校准模型。评分器判错比任务做错更麻烦，因为会拿着错分数把产品往错方向改。
