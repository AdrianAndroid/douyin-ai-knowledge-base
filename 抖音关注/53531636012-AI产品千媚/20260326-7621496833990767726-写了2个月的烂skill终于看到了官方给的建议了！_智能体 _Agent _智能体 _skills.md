盘点 Skill 误用场景
技能并非万能神药，在以下场景中不建议使用，强行套用反而会导致输出僵化或适得其反：

Agent 天生具备的能力：如翻译、润色、总结等，直接使用即可。
一次性或偶发任务：技能的核心价值在于复用，仅做一次的任务不值得封装。
创意发散类任务：如头脑风暴、产品命名，过度约束会限制随机性和创造力。
局部行为偏好：如表述语气正式度，用一句话提示词即可搞定。
连接外部系统：这属于 MCP（Model Context Protocol）的职责，技能不应替代其进行工具连接。
毫无规律的输出：每次需求不同时，强行套用固定流程无法提供有效帮助。

明确 Skill 开发前提
在决定编写技能前，需通过以下三个问题进行评估，若任一答案为 “否”，则建议先用对话解决：

能力基线：不用技能，Agent 能否做到八十分的效果？
复用频率：这件事情是否会重复发生（如至少十次以上）？
知识注入：是否需要注入 Agent 不知道的专有知识，而不仅仅是约束其行为？

模式一：知识注入
该模式旨在解决 Agent 不了解团队内部约定（如代码规范、变量命名规则）的问题。设计时需注意：

职责划分：将核心触发说明写在 skill.md 中，详细规则放入 references 按需加载，避免主文件过长干扰模型判断。
精准触发：描述需具体，例如明确写出 “当用户编辑 Python 代码时触发”，而非宽泛地描述为 “帮助团队写代码”。

模式二：文档生成
通过为 AI 配备固定模板，确保输出格式的一致性（如周报生成）。核心在于三层文件的职责分离：

流程控制：skill.md 定义加载模板、收集信息、填充生成的执行步骤。
结构控制：templates 存放完整的报告模板，规定输出的长相。
质量控制：references 存放语气、字数等风格指南。 这种分离使得修改模板或风格时互不干扰，极大提升了可维护性。

05:57
模式三：质量审查
该模式将人工检查的规则自动化，适用于如社交媒体发布前的违禁词、品牌名称、话题标签审查等场景。 核心思路是将 “检查什么” 与 “怎么检查” 分离。执行协议写在 skill.md 中，而具体的检查清单（Checklist）放在 references 里。当平台规则更新时，只需修改清单文件即可，无需改动技能本身的结构。

06:59
模式四：信息收集
在执行复杂任务前，通过多轮提问帮助梳理思路并提升准确率。这是结构最简单的模式，仅靠一个 skill.md 文件即可实现。 设计时需把握三个要点：一是明确阻断指令，防止 Agent 在收集完信息前就开始输出；二是一次只问一个问题，避免给用户造成负担；三是设定逻辑顺序，按照 “为什么 - 用什么 - 不能做什么” 的脉络依次提问。

08:36
模式五：流程编排
适用于步骤多、有强依赖关系的长链路任务（如电商售后处理、合同审查）。设计时需将步骤拆解并分布在不同文件中：

明确依赖与边界：在 skill.md 中写清每一步的输入、输出、通过条件及失败路径，避免 Agent 自行发挥或在出错时随机选择。
分文件管理规则：在 references 中按步骤拆分文件（如 step1 判断规则、step2 模板等），按需加载，防止上下文溢出或规则冲突。

总结 Skill 设计原则
五大模式的共同设计原则是 “职责分离”，即模板、规则、流程各自独立，互不干扰。技能设计的方法论归根到底，就是将模糊的意图转化为结构化的规范，拆得越细、定义得越清楚，技能的执行就越稳定。
