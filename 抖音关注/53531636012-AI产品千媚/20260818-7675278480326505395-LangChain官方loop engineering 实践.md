这是一期解读 LangChain 官方文章《The Art of Loop Engineering》 的技术分享，作者是 AI 产品千媚。核心观点是：Agent 能连续跑完任务，只说明 Demo 成功；结果可验证、失败可返回、业务可持续，才算接近真正的产品交付。

四层 Loop，对应四个时间尺度

层级	解决什么	关键机制
Agent Loop	一次行动	模型调用工具、看结果、继续执行，直到自己判断 “做完了”
Verification Loop	一次任务	结果先交给 Grader，按预设 Rubric 检查链接是否有效、CI 是否通过、改动范围是否越界；不通过就把原因反馈回去重做
Event-driven Loop	持续发生的业务	监听 Slack 频道等事件自动触发，产品要处理排队、重复事件、并发冲突、失败重试、状态恢复
Hill-climbing Loop	跨多次任务的系统演进	汇总多次运行的 trace 找系统性失败模式，再改 prompt、工具、上下文、Memory、Skills 或 grader

最值得记住的两个判断

一是 Verification 的本质是权力转移：从 “执行者自己宣布完成”，变成 “产品用独立标准定义什么叫可交付”。作者点出 AI 产品最常见的错误 —— 把流程状态当业务结果：生成了内容、接口返回成功、模型没报错，都不等于用户要的数据准确、链接可用、改动没越界。

二是 Hill-climbing 不等于让 Agent 自己改 prompt 直接上线。如果 Rubric 本身错了，系统只会更高效地优化到错误方向；可靠改进仍需候选版本、离线评测、回归测试、人工审核、小流量验证和回滚。

作者用 “文档 Agent” 贯穿全文：它要克隆代码仓库、搜文件、理解代码与文档差距、改内容、查 diff、开 PR。这个例子说明 “工具调用成功、文件生成成功、模型说完成” 都不是业务意义上的完成。

结尾作者认同文章的一个判断：自动化不是把人移出循环，而是重新安排人出现的位置—— 转账、删数据、改数据库等敏感操作前人工确认，结果写入核心系统前审批，harness 新版本部署前人类评审。人的角色从 “提醒下一步” 变成 “定义目标、验收标准和行动边界”。

评论区也有现实反馈：不少人吐槽 LLM 最后阶段偷懒、UI 写飞、突然说 “改动太大不想做”；也有人算账 —— 一次循环做到 95%，加上多轮验证补最后 5%，时间可能增加十倍以上。这正好对应视频里 Event-driven 和 Verification 两层的成本问题。

想继续的话，可以聊聊 Grader 和 Rubric 具体怎么写，这是整套方案里最容易做歪、也最决定成败的一环。
