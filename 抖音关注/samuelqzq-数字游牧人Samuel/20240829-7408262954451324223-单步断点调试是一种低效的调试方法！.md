云峰的观点（作者转述）

交互式调试器是软件史上的重大发明，但和图形界面一样，是 “牺牲效率换低学习门槛”，本质低效。
他 2005 年前重度依赖 Turbo C、Visual C++ 调试器，转跨平台开发后 Linux 图形调试外壳（insight gdb 等）不好用，才开始反思。
替代方案：写简洁代码、多做 Code Review、有意识地加日志输出；调试器只能跑真实输入的那一条路径，且缺乏回溯能力，而大脑推演可以 “并行” 考虑所有分支。
判断复杂度看 McCabe 圈复杂度（分支数量），高内聚低耦合的模块划分让人脑一次只处理一小块；长期 review 别人代码能训练这种切分能力。
名言式表达：“打开编辑器盯着代码看，盯久了 bug 自然就高亮出来了”“代码是给未来维护者的一封情书”。

博主的反驳与补充

不同意 “盯代码就能看出 bug”：视野盲区真实存在，看变量运行到某行的值往往一下恍然大悟。
认为两者应结合：先用断点把问题锁定在两个断点之间，再读中间代码，事半功倍。
举 C++ 为例：虚函数、重载、模板实例化让局部代码有多种解释，不跳进去根本不知道调到哪里，这类项目必须 debug。
加日志要重新编译，项目大时反复加日志也很费劲；调试器在程序崩溃时 attach 进程看现场仍有奇效。
顺带吐槽：Code Review 在国内常流于形式、拖慢效率；还聊到 ACM 三人一机、纸面手算代码的训练经历，以及杭州等地中小学早接触编程的教育差异。

评论区共识：断点、日志、Code Review 不是对立关系，看场景 —— 多线程、多服务并发、递归锁死、内核崩溃时断点确实低效；也有人提醒 Visual Studio 支持把断点位置拖回栈帧重跑，不必从头再来。
