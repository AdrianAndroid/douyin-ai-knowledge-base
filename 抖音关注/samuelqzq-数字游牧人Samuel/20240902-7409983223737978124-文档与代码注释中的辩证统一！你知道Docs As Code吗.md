视频讲的是 Docs as Code（文档即代码）：作者主张把技术文档用 Markdown 写进代码仓库，而不是散落在 Word 文件里。他自称在微软工作时就向老板提过这个建议，现在做基于 Chrome 的项目，更认同这个思路。

核心观点：文档和注释是同一件事的不同层级

作者在白板上画了一个从上到下的层级：Repo → Modules → File → Function → Lines of code。越往上，文档越像独立文档（docs，用 markdown 写）；越往下，越像代码注释（comments）。他的判断是：文档也是注释，注释也是文档，只是级别不同。

为什么要把文档放进仓库

用 Word 存在仓库外，搜关键词搜不到，也没人知道前人写过哪些文档；做浏览器项目时有成千上万份文档，找起来很痛苦。
放进仓库后，看代码时能顺手搜到旁边的文档。
Markdown 文档可以走 PR 流程，和代码一起合并，之后看代码能追溯到当年的 PR，看文档也能找到当时的代码，两边不会失联。
删文件或改文件名时，测试和检查能发现文档里的链接失效，从而拦住合并；文档放在仓库外就做不到。

为什么越下层的注释越不容易过期

改一行代码时，你一定会看到那行旁边的注释，顺手就改了；而文件头、模块级、仓库级的文档，不熟悉的人根本不会去动，久而久之就过期了。作者提到常见现象：新员工看模块文档，发现和代码对不上，甚至文档里提到的文件名在代码里已经不存在了。

一个边界

作者也承认，这套做法在开源项目里更容易推行：Chromium 作为开源项目，基本要求用 Markdown 写文档，否则外部的人看不懂代码。但很多公司内部项目做不到这一点。

评论区里，一位自称在 AWS 做 doc as code 的用户说，他们把文档细化到每个函数和类，认为对个人知识积累和企业复用都有价值；也有人补充，传统项目里大部分中间文档生命周期本来就不长，文档主要作用是指导开发和沟通协调。
